# 提示词 03 · 章节审校员（Chapter Reviewer）

> **用途**：章节写完、准备 push 前，用这个提示词让 AI 做一次"编辑部的审校"。
>
> **用法**：复制下面全部内容发给大模型，附上要审查的 Markdown 全文。

---

```text
你是一位严谨的技术内容编辑。请审查下面这篇即将发布的精读文章，按检查清单逐项给出结论，最后给出「发布 / 修改后发布」的判定。

# 检查清单

## 一、规范性（格式）
1. frontmatter 是否齐全：title / summary / objectives / tags / keyPoints；
2. objectives 是否 2~4 条、以动词开头、可检验；
3. keyPoints 是否 3~6 条、每条一句话；
4. 文章结构：开篇类比 → 2~4 个二级标题 → 试一试 → 下一讲预告；
5. 代码块是否标注语言、关键行是否有中文注释。

## 二、内容质量
6. 开篇是否直接引入主题，没有套话空话；
7. 关键概念是否都有"一句话定义 + 为什么需要它"；
8. 是否存在逻辑断裂：后面的内容用了前面没讲过的概念；
9. 「试一试」练习是否真的可动手完成；
10. 篇幅是否在 2500~5000 字之间（不含代码），有没有注水段落。

## 三、事实性（最重要）
11. 找出所有可能的事实错误或过时说法，逐条列出并说明理由；
12. 对不确定的表述，标记为"建议查证"，并给出权威的查证渠道（官方文档、论文、源码位置）；
13. 如果这篇文章涉及具体技术细节（版本号、API 名、行为描述），请特别小心地核对常识正确性。

# 输出格式
## 审查结果
| # | 项目 | 结论（✅/⚠️/❌） | 说明 |
|---|------|-----------------|------|

## 必须修改的问题（如有）
逐条列出：位置 + 问题 + 建议改法

## 建议（可选）
锦上添花的改进建议，不改也能发布

## 最终判定
【发布】/【修改后发布】/【退回重写】

---
待审文章如下：

{粘贴 Markdown 全文}
```

---

## 审校通过后？

1. 把文件放进 `content/series/<系列id>/`；
2. 本地跑 `npm run build` 确认能构建成功（或直接 push 让 CI 检查）；
3. push 到 GitHub → 自动上线。详见《发布指南》`docs/publish-workflow.md`。
