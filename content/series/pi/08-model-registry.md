软件工程里有一条铁律：**会变的东西，别让人手写**。大模型界的价格、上下文窗口、模型上下线，几乎是按月甚至按周在变。如果 pi 把上千个模型的 `cost` / `contextWindow` 写死在源码里，维护者会累死，也必然过时。

pi 的做法是：**模型目录是一份"生成的代码"**——`models.generated.ts`。本讲我们看这份文件怎么来、谁生成、以及老式接入如何优雅兜底。

## 一、结论：模型元数据是生成的，不是手写的

打开 `packages/ai/src/models.generated.ts`，第一眼就是两行醒目的警告：

```ts
// This file is auto-generated by scripts/generate-models.ts
// Do not edit manually - run 'npm run generate-models' to update

import { AMAZON_BEDROCK_MODELS } from "./providers/amazon-bedrock.models.ts";
import { ANT_LING_MODELS } from "./providers/ant-ling.models.ts";
import { ANTHROPIC_MODELS } from "./providers/anthropic.models.ts";
// … 几十个供应商的模型常量 …
```

逐行：

- 第 1 行点明生成器：`scripts/generate-models.ts`。第 2 行是给人类的**硬规矩**——"不要手动编辑，跑 `npm run generate-models` 来更新"。
- 文件主体是 `import` 各家供应商的模型常量（如 `ANTHROPIC_MODELS`），最后汇成一个 `MODELS` 对象（文件末尾可见 `"anthropic": ANTHROPIC_MODELS, …` 的字典）。第 07 讲 `providers/all.ts` 里的 `anthropicProvider()` 调 `Object.values(ANTHROPIC_MODELS)`，用的正是这里导出的常量。

**为什么必须生成、绝不能手改？** 三个理由：

1. **规模**：几十家供应商、上千个模型，每个都有 `id` / `cost` / `contextWindow` / `maxTokens` / `input` 模态等字段。手写既不可能也无意义。
2. **易错**：价格少个零、窗口写错数量级，运行时才会暴露，且极难排查。生成器从权威数据源（供应商官方清单）拉取，正确性由脚本保证。
3. **单一事实来源**：所有 `Provider` 共享同一份 `MODELS`，避免 A 文件写一份、B 文件又抄一份造成的漂移。改一处、生成一次，全量更新。

> 所以牢记一条**纪律**：任何想"顺手改 `models.generated.ts`"的冲动都是错的。要改，去改生成器的数据源或脚本，然后重跑 `npm run generate-models`。

## 二、generate-models 脚本：从清单到类型安全目录

"跑 `npm run generate-models`"具体是什么？在 `packages/ai/package.json` 的 `scripts` 里（`:52`）：

```json
"scripts": {
  "generate-models": "node scripts/generate-models.ts --strict",
  "hydrate-model-data": "node scripts/generate-models.ts --strict --data-only",
  "generate-model-catalog": "node scripts/generate-models.ts --strict --json-only --json-output ../../.artifacts/model-catalog",
  "generate-image-models": "node scripts/generate-models.ts --strict"
}
```

逐行：

- `generate-models`（`package.json:52`）是主命令：`node scripts/generate-models.ts --strict`。`--strict` 意味着数据源有缺失或异常字段时**报错而非静默跳过**——保证生成物质量。
- `hydrate-model-data`（`:53`）带 `--data-only`，只刷新"动态数据"（如实时价格），不动类型骨架。
- `generate-model-catalog`（`:54`）带 `--json-only`，产出一份 JSON 目录到 `.artifacts/model-catalog`，供外部工具（CLI 补全、文档站）消费。
- 注意 `build` 脚本（`:57`）是 `"npm run generate-models && npm run build:offline"`——**每次构建先 regenerate 再编译**，确保产物永远基于最新目录。

脚本本体在 `packages/ai/scripts/generate-models.ts`，它读取供应商清单（`providers/*.models.ts` 里那些常量、以及可能的外部数据源），经过校验后吐出 `models.generated.ts`。因为走的是 TypeScript 类型（`Model<TApi>`），生成出来的 `MODELS` 天然类型安全——第 07 讲 `getBuiltinModel(provider, id)` 能返回精确类型的 `Model`，靠的就是这层生成保证。

**为什么不用运行时拉取、而要生成静态文件？** 因为静态生成让 `pi-ai` 在离线、无网环境下也能完整工作，且构建期就锁定模型能力，避免运行时网络抖动导致的能力不确定。

## 三、compat 层：withEnvApiKey 如何兜底旧式 API Key

生成目录解决了"有哪些模型"，但"怎么鉴权"还有历史包袱。`pi-ai` 有一层 `compat`（兼容）代码，其中 `withEnvApiKey`（`compat.ts:222`）专门处理"调用方没显式传 Key，就从环境变量兜底"：

```ts
function withEnvApiKey<TOptions extends StreamOptions>(
  model: Model<Api>,
  options: TOptions | undefined,
): TOptions | undefined {
  if (hasExplicitApiKey(options?.apiKey)) return options;          // 已显式给 Key，直接用
  const apiKey = getEnvApiKey(model.provider, options?.env);       // 否则按 provider 查环境变量
  if (!apiKey || apiKey === AMBIENT_AUTH_MARKER) return options;  // 没有也不强行塞
  return { ...options, apiKey } as TOptions;                       // 有则合并进 options
}
```

逐行：

- 第 4 行 `hasExplicitApiKey` 检查 `options.apiKey` 是否非空。调用方已经在请求级给了 Key（比如某次临时用别的 Key），就**原样返回**，不动它——显式优先。
- 第 5 行 `getEnvApiKey(model.provider, options?.env)` 按 `model.provider` 去查该供应商对应的环境变量 Key。第 07 讲 `anthropicApiKeyAuth()` 的 `resolve` 也是查环境变量，但那是 `Provider.auth` 路径；这里是 `compat` 的**另一道**兜底，服务于旧的 `stream(model, ctx, options)` 直调风格。
- 第 6 行如果连环境变量都没有（或标记为"环境已认证"的占位符 `AMBIENT_AUTH_MARKER`），就返回原 `options`，不强行注入。
- 第 7 行只有"确实有环境变量 Key"时，才 `return { ...options, apiKey }`——**浅拷贝后注入**，不污染原 `options` 对象。

它的存在意义是**向后兼容**：早期 pi 的调用约定里，API Key 常靠环境变量隐式提供。`withEnvApiKey` 让新代码既能接受显式 Key，又不会让老调用方（只配了环境变量）突然失效。这正是"兼容层"该有的样子——不改变新结构，悄悄接住旧习惯。

## 四、env-api-keys：密钥环境变量名的唯一出处

`withEnvApiKey` 调的 `getEnvApiKey` 最终去哪查？变量名从 `env-api-keys.ts` 来。看第 31 行附近：

```ts
export const ANTHROPIC_AUTH_TOKEN_ENV = "ANTHROPIC_AUTH_TOKEN";
export const ANTHROPIC_OAUTH_TOKEN_ENV = "ANTHROPIC_OAUTH_TOKEN";
export const ANTHROPIC_API_KEY_ENV = "ANTHROPIC_API_KEY";        // :31
```

逐行：

- 这三个常量把"Anthropic 相关的环境变量名"**集中定义**在一处。`ANTHROPIC_API_KEY_ENV`（`:31`）就是用户最熟悉的那枚 `ANTHROPIC_API_KEY`。
- 第 07 讲 `anthropic.ts:5` 正是 `import { ANTHROPIC_API_KEY_ENV, … } from "../env-api-keys.ts"`，然后在 `anthropicApiKeyAuth().resolve` 里逐个尝试 `ANTHROPIC_AUTH_TOKEN_ENV`、`ANTHROPIC_OAUTH_TOKEN_ENV`、`ANTHROPIC_API_KEY_ENV`——顺序就是凭据优先级。

**为什么要把变量名收进一个文件、而非各处硬编码字符串？** 因为变量名本身就是"契约"：用户按文档设了 `ANTHROPIC_API_KEY`，pi 必须到**同一个字符串**去读。一旦散落在十几个文件里写成 `"ANTHROPIC_API_KEY"` 和 `"anthropic_api_key"` 两种拼法，就会出现"设了 Key 却不生效"的幽灵 bug。集中常量让拼写只有一处真相，重构时改一个地方即可全局生效。

> **知识拓展：生成目录 + 兼容层 = 稳定的接入面**
> 把本讲和第 07 讲连起来看：`models.generated.ts` 给出"模型有哪些"，`env-api-keys.ts` 给出"Key 去哪读"，`createProvider` 给出"怎么发请求"，`withEnvApiKey` 给出"老调用方怎么还能用"。这四块拼起来，供应商接入面既**新鲜**（生成）又**宽容**（兼容），还**可插拔**（第 07 讲的 `setProvider`）。这正是基础库该有的成熟度。
