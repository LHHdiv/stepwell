第 43 讲保证"不改坏"，但写代码时你还是要反复跑、反复看、反复修。这一讲看 pi 的**开发调试回路**：怎么让"改一行 → 看到效果 → 定位问题"尽可能快。

## 一、先结论：快回路靠三件事

一个顺手的调试回路要缩短三个延迟：

1. **启动延迟**：从改代码到跑起来要快；
2. **反馈延迟**：效果要立刻可见；
3. **定位延迟**：出问题要能快速知道"坏在哪"。

pi 在这三点上各有对应机制。

## 二、启动：从源码跑起来

回忆第 04 讲：`pi` 是 npm workspaces monorepo，依赖 Node ≥ 22.19。开发期流程是：

```
npm install --ignore-scripts   # 装依赖（忽略生命周期脚本，快且安全）
npm run build                   # 构建所有 workspace 包
用仓库脚本（如 ./pi-test.sh 一类）以源码模式启动 pi
```

仓库提供的"源码启动脚本"省去了"先发版再装"的麻烦——你改完 `packages/*` 里的源码，构建后直接跑，改动即时生效。这把"启动延迟"压到一次构建以内。

## 三、反馈：扩展热重载

如果你在调的是**扩展**（第 21–22 讲），反馈还能更快。扩展经 `jiti` 加载（第 22 讲 `loader.ts:436`），而 jiti 支持**缓存失效（invalidate）后再加载就是新代码**。于是：

- 改 `cwd/.pi/extensions/foo.ts`；
- 让 jiti 缓存失效；
- 重新加载扩展——不用重启整个 pi。

这把"改扩展 → 看效果"的循环从"重启进程"缩短到"重载模块"。对扩展开发者，这是极大的提速。

> **知识拓展**：热重载（HMR）的核心都是"模块级替换而非进程级重启"。Vite/Webpack 的 HMR、React Fast Refresh、pi 的 jiti invalidate，是同一思想在不同运行时的落地。

## 四、定位：遥测与评测当探针

最难的"定位延迟"，pi 不靠你往代码里狂加 `console.log`，而是靠两样结构化工具：

**探针一：遥测 span（第 37 讲）**。一次 AI 调用慢了？看 `AI_TELEMETRY_SCHEMA` 记的 span：模型、token、延迟、错误码一目了然。span 是**带字段的结构**，比 `console.log("here")` 能直接聚合、能按维度筛选。

**探针二：轨迹评测（第 33 讲）**。一个行为"偶尔坏"最难调，因为手调复现不了。把它写成一条 `vitest-evals` 用例：固定的输入、可断言的输出。坏行为一旦能被"跑成失败"，你就有了**可重复的实验台**——改代码、重跑、看绿，比凭感觉调稳得多。

两样合起来：遥测告诉你"线上哪慢/哪错"，评测让你"在本地稳定复现并验证修复"。这比散落的 log 强在"结构化、可聚合、可重复"。

## 五、TUI 调试友好性

顺带一提：第 29 讲差分渲染自带调试友好——组件状态一变就重画，你改了渲染逻辑不用重启，效果立刻在终端反映。状态驱动 UI（第 30–32 讲）天然比命令式 UI 好调试，因为"所见即状态"，没有隐藏的绘制副作用。

## 六、试一试

1. 回到第 04 讲，确认你本地能否 `npm run build` 后跑起 pi（至少跑通 interactive 模式的一次对话）。
2. 写一个最小扩展（参考 `examples/extensions/hello.ts`），改它的 `execute` 打印一句话，体验"重载扩展" vs "重启进程"的快慢差。
3. 思考：如果把"线上报错的 span"直接喂给第 33 讲的评测框架当一条复现用例，调试回路会怎么升级？（提示：可观测性数据 → 评测输入，闭环自动形成。）
