第 00 讲我们列出 pi 相对 dsh 的"五道缺口"，其中一道叫**信任缺口**：pi 没有内置权限系统。当时埋下伏笔——pi 把"信任"推到了**架构形态**上，而不是写一堆 `if (allowed)`。这一讲揭晓这个形态是什么：**把 pi 拆成两个进程**。

## 一、先结论：一个内核，两个进程

pi 运行时至少有两个角色：

- **本地 agent（coding-agent）**：跑在你机器上，真正"动手"——读文件、跑命令、调工具。它是**不可信**的，因为它能执行任意代码。
- **受信任 server（pi-server）**：持有 API key，负责和 LLM 对话。它是**可信**的，因为它只做"转发模型调用"这一件 confined 的事。

两者用第 09–10 讲讲的 framed CBOR 协议通信。本讲先讲"为什么非要拆"，后三讲再讲"各自长什么样"。

## 二、动机一：密钥隔离

最朴素也最要命的理由：**API key 不该出现在会跑任意代码的进程里**。

本地 agent 能执行 shell、能读你磁盘上的任何文件。如果密钥也在这个进程里，一旦某个工具被恶意提示注入利用，密钥瞬间泄露。把密钥挪到独立的 server 进程，agent 进程**内存里根本不存在密钥**——它要调模型，只能发"请帮我问 LLM 这句话"的请求给 server，server 用自己的 key 去问。

> **知识拓展**：这不是 pi 的发明。经典的"密钥永不落客户端"原则，在 AWS STS、数据库代理（如 ProxySQL）里都是同一套路。pi 把它做成了默认架构，而不是"记得别把 key 写进 agent 配置"。

## 三、动机二：风险隔离

本地 agent 是"有能力作恶"的——它能 `rm -rf`，能 `curl` 外网，能读 `.env`。而 server 的攻击面极小：它只接收"模型请求"、返回"模型回复"。即便 agent 被攻破，攻击者拿到的也只是一台已被授权的机器上的局部控制权，**拿不到能刷爆账单的模型密钥**。

进程边界由操作系统保障：两个进程地址空间隔离，agent 没法"偷偷读"server 的内存。这比在代码里写 `if (!allowed) throw` 硬得多——后者只是约定，前者是内核强制。

## 四、动机三：部署弹性

更深远的好处是**部署形态可变**：server 不一定在你本机。你可以把 server 跑在一台受信任的远程主机（或公司内网的密钥网关）上，本地机器只跑 agent。于是：

- 开发者的笔记本上**一个密钥都没有**；
- 密钥集中管理、可轮换、可审计；
- 本地 agent 即便被盗，攻击者也只是拿到一个"没钥匙的司机"。

这正好解释了第 03 讲的哲学：**pi 不内置权限系统，因为它把"谁能调模型"这个问题，交给了"server 部署在哪"这个运维决策**。信任边界 = 进程边界 = 部署边界。

## 五、和"五道缺口"的咬合

回到第 00 讲那张表：dsh 用「权限系统（approvals）」堵信任缺口；pi 用「进程拆分」堵同一个缺口。两种解法各有取舍——

- dsh 的权限系统让**同一个进程内**也能细粒度放行/拒绝；
- pi 的进程拆分让**跨机器**部署天然安全，但同机内 agent 进程本身仍需用户信任（它确实能跑命令）。

没有谁更好，只有适配场景不同。看清这一点，你才算真正读懂了"两个优秀 harness 的不同野心"。
