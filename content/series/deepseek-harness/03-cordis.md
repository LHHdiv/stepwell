上一讲的流程图里，`ctx.tools`、`ctx.llm`、`agent/pre-step` 这些名字反复出现。它们全部来自同一套机制——**Cordis**，dsh 以 vendor 方式内嵌在 `vendor/` 目录里的插件框架。官方文档甚至说："不存在需要打补丁的特权内核"。这一讲我们拆这块插线板。理解了它，后面读任何包的源码你都会看到似曾相识的形状。

## 一、五个核心概念

官方入门文档把 Cordis 浓缩成五句话，我们逐句展开。

**① 插件是实现 Service 的对象。** 它可以是一个带可选 `inject` 和 `apply(ctx)` 字段的函数，也可以是一个 Service 子类。示意（简化伪码，重在形状）：

```ts
// 一个最小插件的"长相"：声明依赖 + 拿到上下文 + 注册行为
export const myPlugin = {
  inject: ['tools'],          // 声明：我需要 ctx.tools 就绪后才启动
  apply(ctx) {
    // 向工具注册表贡献一个新工具（可逆副作用的注册）
    ctx.effect(() => ctx.tools.register({ /* 工具定义 */ }))
  },
}
```

**② 上下文（Context）是服务的容器。** 每个服务占据一个稳定的 `ctx.<key>`——`ctx.sessions`、`ctx.llm`、`ctx.tools`……其他插件通过 key 找服务，而不是 import 具体实现。这是关键设计：**面向插槽编程，而非面向零件编程**。想换掉文件系统提供方？只要新提供方还挂 `ctx.fs` 这个键，所有消费方无感知。

> 💡 **知识拓展：这就是控制反转（IoC）**
> 传统写法里，A 需要文件系统就自己去 import 某个具体的 FS 类——依赖被写死。IoC（Inversion of Control，控制反转）把这个权力"反转"给容器：组件只声明"我需要一个 fs"，具体给哪个实现由装配时的插件树决定。Spring、Angular 都是这个思路。好处：实现可替换、测试时可注入假实现（dsh 要求 100% 测试覆盖，正是靠这种可注入性达成的）。

**③ 通过 inject 声明服务依赖。** 插件声明所需服务后，会等它们就绪才启动。加载顺序由依赖图自动推导，不需要手写"先启动 A 再启动 B"的启动脚本。依赖即顺序。

**④ 类型化事件用于通信。** 服务通过 TypeScript 的声明合并（declaration merging）注册事件名和参数类型，然后以四种模式之一分发（下一节详表）。类型化意味着：你 emit 一个拼错名字的事件，编译器当场报错——事件系统不是字符串魔法，而是有编译期保障的契约。

**⑤ 注册是可逆的副作用。** 这是 Cordis 最优雅的一环：所有注册——提示词片段、工具 schema、适配器、监听器——都通过 `ctx.effect()` 或 `ctx.on()` 安装，插件卸载或热重载时会按预期撤销。类比酒店房卡：退房时门禁自动失效，不需要你挨个房间去关灯。"拔插头不留火花"，是一切皆插件能成立的前提。

## 二、四种分发模式

每个事件属于且仅属于一种分发模式，这是事件公开约定的一部分：

| 模式 | 是否 await | 顺序 | 返回值 | 直觉理解 |
|---|---|---|---|---|
| `emit` | 否 | 注册顺序逐个观察 | 无 | **广播**：贴个公告，大家看看就行 |
| `waterfall` | 否 | 注册顺序逐层包装 | 有 | **洋葱**：层层把关，层层加工 |
| `parallel` | 是 | 所有监听者并行 | 无 | **群呼**：同时通知，互不等待 |
| `serial` | 是 | 注册顺序依次执行 | 有 | **听证会**：按序发言，汇总意见 |

对照第 02 讲的流程图验证一下你的理解：`assistant/chunk` 这种"通知 UI 更新"的事件该用哪种？——emit 或 parallel，因为它只是广播事实。`tools/execute` 这种"要不要放行这次执行"呢？——waterfall，因为需要把关链。`agent/turn-stopping` 这种最终裁决？——serial，按序收集意见后一锤定音。

> 💡 **知识拓展：为什么 emit 和 waterfall 不 await，parallel 和 serial 要 await？**
> 这取决于语义需求。emit/waterfall 用于同步的观察与包装——链条短、要求快，异步化反而引入复杂度。parallel/serial 用于可能耗时的异步工作（比如调用外部服务），框架需要 await 所有监听者完成才能继续。设计事件系统时先问"监听者会不会做慢事"，再选模式。

## 三、waterfall 的洋葱语义

waterfall 值得单独一节，因为它是 dsh 最常用的扩展手法。监听者收到的签名是 `(...args, next)`：

- 调用 `next()` → 执行下游监听者，其返回值交回给你，你可以包装后再返回；
- 不调 `next()` 直接返回 → **短路**，下游全部跳过。

协作式监听者的典型姿势是"改一改共享对象，然后委托"；策略型监听者的典型姿势则是"拥有决策权时短路"——比如审批插件判断这条命令危险，直接短路返回拒绝，后面的执行环节根本不会发生。官方实践规则说得很清楚：**仅当监听者必须在普通注册之前运行时才用 `prepend: true`**——绝大多数场景下，注册顺序就是责任链顺序。

如果你用过 Koa 或 Express 的中间件，会发现 waterfall 就是同一个洋葱模型：请求穿过一层层中间件到达核心，响应再原路穿回来，每层都有机会加工或拦截。

## 四、"新行为的归属位置"

Cordis 给了扩展自由，也带来了纪律问题：一个新功能到底该写成什么？官方架构文档有一张著名的归属表，节选几行感受一下：

```text
添加模型提供方        → 在 ctx.llm 上注册适配器
添加面向模型的能力    → 在 ctx.tools 上注册工具
限制启动的进程        → 使用 ctx.sandbox 后端包装 argv
拦截请求、工具或轮次  → 监听 agent/* 或 tools/* 事件
添加持久会话状态      → 扩展 SessionEventMap（卷二主角）
```

这张表是本系列的暗线：卷四到卷七讲的每一个器官，都是在回答"某个能力该挂在哪张表的哪一行"。你现在只需要建立这个意识——**在 dsh 里，加功能 ≠ 改代码，而是 = 选对插槽挂插件**。
