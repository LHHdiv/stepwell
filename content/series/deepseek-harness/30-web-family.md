协议三连之后来点轻松的。智能体的高频需求之一是上网查资料，dsh 的 `packages/web/` 用五个小包优雅地解决了它。这个家族没有复杂的协议握手，但它是**能力 seam 复用**的最佳教学案例——麻雀虽小，五脏俱全。

## 一、五包编队

```text
packages/web/
├── web-search-deepseek      # DeepSeek 搜索适配器
├── web-search-exa           # Exa 搜索适配器
├── web-search-perplexity    # Perplexity 搜索适配器
├── web-fetch-http           # HTTP 抓取器
└── tool-web                 # 面向模型的统一工具
```

对照 seam 三角色（第 03 讲）：web 搜索的 Service Definition 定义"一次网络搜索长什么样"；三个适配器是并列的 Service Provider；tool-web 是 Consumer——把能力翻译成模型可调用的工具。

## 二、为什么三家引擎只给一个工具？

站在实现者角度最偷懒的做法是给模型三个工具：search_deepseek、search_exa、search_perplexity。dsh 偏不——统一成一个搜索工具，引擎选择藏在配置里。理由有三：

1. **模型的选择负担**：每多一个工具，模型就多一次"用哪个"的判断。三个功能雷同的搜索工具只会稀释注意力、拉低调用准确率（第 18 讲的工具描述黄金法则在此放大）；
2. **运维自由**：今天用 Exa 明天换 Perplexity？改一行配置挂载不同的 Provider 插件，模型的工具菜单、提示词里的工具指引、历史对话里的调用记录全部无需变动；
3. **组合策略成为可能**：Provider 层甚至可以做主备切换或结果融合，上层毫无感知。

这是"面向插槽编程"最日常的应用：**用户可见的能力稳定，背后的供应商随意轮换。**

## 三、fetch 的降噪流水线

web-fetch-http 负责第二步：拿到 URL 后抓回全文。但原始 HTML 是给浏览器看的——脚本、样式、导航栏、广告横幅……直接塞进模型上下文等于往胃里倒垃圾。所以抓取结果的必经之路：

```text
HTTP 响应 → HTML 解析 → 正文提取（去脚本/样式/噪声）→ 文本化 → 截断/spill 策略 → 进历史
```

正文提取是个经典的脏活（Readability 类算法的领地），而末端的截断与 spill 衔接你已经很熟了：一篇万字长文不该整段灌进对话——外溢存全文，历史留预览与定位（第 16 讲）。**每个环节都在为 token 预算精打细算**，因为模型上下文是全系统最昂贵的资源。

## 四、搜索 + 抓取：两步走的漏斗

为什么搜索和抓取是两个工具而不是合体成"搜并读全文"？观察人类研究者的工作流：先广撒网看摘要清单 → 判断哪几篇值得细读 → 点开细读。两步走把这个漏斗交给模型自己控制：

- 第一步返回标题+摘要+URL 清单，token 成本极低；
- 第二步按需抓取选中的 URL，成本花在刀刃上。

如果合成一步"搜索即读全文"，要么烧钱（每条结果都抓），要么阉割（每篇只给开头）。**把中间决策权留给推理者**，是工具粒度设计的一条金律——它和第 19 讲"最小惊讶原则"一起构成工具设计的双翼。

> 💡 **知识拓展：Agent 的联网姿势谱系**
> 从重到轻有四种：①自带完整浏览器（能点按钮填表单，重但全能）；②HTTP 抓取+正文提取（本讲的路线，覆盖九成需求）；③纯搜索 API（只有摘要清单）；④RAG 式预建索引（最快但范围受限）。dsh 选了②+③的组合拳，把①留给专门的 browser 工具生态（可以经 MCP 接入！）。看清这条谱系，你就明白为什么"要不要给 Agent 上浏览器"不是立场问题而是场景问题。
