第 34 讲结尾说后台能力依赖"可复用的指令包"。本讲就拆这个包：**skill（技能）**。一句话定义：skill 是一份结构化的 Markdown 指令文档，教智能体在某类任务上"怎么做得更好"——比如"本仓库的代码提交规范""部署到生产的操作手册"。它让智能体的知识可以**模块化地安装与分享**。

## 一、四包编队

```text
packages/skill/
├── skill/               # 纯提供方注册表（ctx.skills）
├── skill-filesystem/    # 本地文件系统的发现实现
├── tool-skill/          # 面向模型的目录 + 加载工具
└── skill-badge/         # 可选的内置示例技能
```

又是熟悉的 seam 三角色加一个示例。`ctx.skills` 接口的自我定位非常克制："纯 provider 注册表。它**不知道** skill 来自本地文件、嵌入式插件数据、HTTP 还是其他后端；提供方通过 `ctx.skills.registerProvider(...)` 注册这些来源。"——注册表只管"有一批技能存在"，来源问题全权交给提供方。

## 二、SKILL.md：一纸约定

本地发现的实现是 skill-filesystem："扫描本地项目、自定义和用户 skill 根目录，解析 `SKILL.md` 或平铺 Markdown skill 文件"。这个设计直接继承了社区已经形成的惯例（Claude Code 等产品的 SKILL.md 格式）：一个目录一个技能，入口是一份带元数据的 Markdown——名字、描述写给模型看，正文写给模型照做。

三个扫描根目录的分层也有讲究：项目级（跟仓库走，团队共享）、用户级（个人跨项目资产）、自定义目录（你说了算）。优先级与合并语义由提供方决定——又是"机制在框架、策略在配置层"。

## 三、两段式加载：上下文经济学

这是 skill 设计中最值得学的工程决策。想象把所有技能全文塞进系统提示词：五十个技能 × 平均两千字 = 十万字常驻开销——每个会话都在为用不到的知识付费。dsh 的解法是**两段式**：

```text
第一段（常驻）：目录 —— 每个技能的名字 + 一句话描述（几十 token）
第二段（按需）：正文 —— 模型判断某技能相关时，用 skill 工具加载全文
```

tool-skill 包提供的正是这两样东西：面向模型的技能**目录**和 **skill 工具**（它的依赖清单 inject: ['agents','tools','skills'] 告诉你它站在三块地基之上）。模型平时只见目录；接到一个部署相关任务时，目录里"deploy-production: 如何安全发布到生产环境"这行描述触发它的兴趣，调用 skill 工具取来全文细读。

这个模式你已经见过三次了：MCP 的目录发现、第 16 讲 spill 的"存外部留定位"、以及数据库领域的索引+行存。**元信息常驻、重内容外置、按需取回**——上下文经济学的通用解。

## 四、badge：一个故意存在的最小样本

家族里有个可爱的成员：skill-badge，唯一的功能是提供一个"dsh-badge"技能——教模型输出官方"powered by dsh"的 Markdown 片段和随包 PNG。看起来像个玩笑？它是精心设计的**教学标本**：

- 它演示了"一个提供方插件的最小完整形态"，想写自己的 skill 提供方？抄它；
- 它展示了默认禁用的发布纪律："以 disabled: true 包含该插件，用户必须显式启用"——连官方自己都不白给用户塞东西，这个姿态本身就是产品哲学的表达。

## 五、skill 与 hooks、subagent 的分工

卷七讲了三种"扩展智能体行为"的方式，做个了断：

| 方式 | 形态 | 改变什么 | 典型作者 |
|---|---|---|---|
| hook（原生插件） | TypeScript 代码 | 运行时行为（拦截、改写） | 开发者 |
| skill | Markdown 文档 | 知识与方法论 | 所有人 |
| subagent | 运行中的智能体 | 执行资源 | 编排者 |

写不了代码的产品经理可以贡献 skill；要改变审批逻辑必须写插件；想让任务并行则派子代理。三者正交，组合使用——好的扩展体系让每种贡献者都能找到自己够得着的那一层。

> 💡 **知识拓展："知识即文件"的力量**
> skill 的本质是把"提示词工程"从代码库里解放出来变成内容资产：版本管理走 git、评审走 PR、分享走复制文件夹。对比把领域知识硬编码进 system prompt 字符串的做法——每次微调都要发版。当你的 AI 产品需要积累领域 know-how 时，先问一句：这部分知识该是代码，还是该是数据？
