想象一家餐厅。客人点单后，后厨发生了一连串事情：接单、备菜、烹饪、装盘、上菜。如果你想把这家餐厅的运作机制搞清楚，最好的办法不是盯着某位厨师，而是先弄明白**有几个岗位、单据怎么流转**。

读 dsh 也是一样。这一讲我们先拿到它的"组织架构图"。

## 一句话定位

dsh 官方文档对它的定义是：一个 **agent harness**——运行智能体的框架。拆开说：

- 它**不包含**大模型本身（模型在 DeepSeek 的服务器上）；
- 它负责模型之外的一切：管理对话历史、决定给模型看什么、执行模型要求调用的工具、把控安全边界。

类比：模型是引擎，dsh 是整辆车——方向盘、油门、仪表盘、安全带都是它装的。

## Monorepo：一仓多包

打开 [仓库根目录](https://github.com/deepseek-ai/deepseek-harness)，你会发现它不是"一个项目"，而是用 pnpm workspace 管理的 **monorepo（单一仓库、多个包）**，共 50 多个包。别被数量吓到——它们是按领域归堆的：

```
deepseek-harness/
├── apps/
│   ├── cli/        # dsh 命令行入口（只有 6 个文件）
│   └── web/        # Web 界面前端壳
├── packages/
│   ├── core/       # ★★★ 核心：session / agent / agent-loop / tools / system-prompt
│   ├── llm/        # ★★  模型 API 层
│   ├── bundle/     # 组合层：把插件打包成发行形态
│   ├── boot/       # 启动装配
│   ├── host/ client/   # 服务端宿主与浏览器组件
│   └── …           # 沙箱、MCP、子代理等能力包
├── docs/           # ★ 官方文档（141 个子系统说明，中英双语）
└── vendor/         # 内嵌的 Cordis 插件框架
```

## 主干六包：一次对话的生命线

真正的主线只有六个包。当你在输入框敲下回车，数据流经它们：

| 包 | 职责 | 类比 |
|---|---|---|
| `core/session` | 把一切记录为事件日志，是唯一事实来源 | 行车记录仪 |
| `core/agent` | 定义"智能体"对外的能力接口 | 司机的操作面板 |
| `core/agent-loop` | 驱动器：发请求→收回复→调工具→循环 | 发动机 |
| `core/tools` | 工具注册表 + 安全执行管线 | 工具箱+安检门 |
| `core/system-prompt` | 决定系统提示词里放什么 | 出发前给司机的简报 |
| `llm` | 与模型 API 对话的统一接口层 | 翻译官 |

记住这六个名字。本系列卷二到卷五会逐个精读它们。

## Bundle：三种发行形态

零件再多，最终要组装成能卖的产品。dsh 用 **bundle（捆绑包）** 的概念做这件事，官方提供三种：

1. **dsh-web-app**：完整产品形态——本地启动一个服务，浏览器里用图形界面；
2. **dsh-base**：只要核心能力，不要界面——适合嵌入你自己的程序；
3. **dsh-headless**：无界面一次性运行——适合脚本自动化，跑完就退出。

同一个内核，三种穿法。这也是"一切皆插件"的直接体现：**产品形态本身也是配置出来的，不是写死的**。
