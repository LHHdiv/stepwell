智能体干活需要任务感。dsh 有三个名字很像的能力——plan、todo、goal——初见容易混淆。本讲把它们放在同一张桌子上对比着拆，重点不在各自的实现细节（那些反而简单），而在**它们为什么必须是三个东西**。

## 一、plan：有计划没牢笼

`packages/plan/` 的 README 第一句就划清了边界：

> Plan mode 是**按 agent 记录的协作状态**，而不是通用模式注册表或能力 seam。

它提供的东西：部署方可配置的引导内容（进入计划模式时给模型的额外指引）、`/plan [message]` 命令进入、`/plan off` 退出、以及经典的 `exit_plan_mode`——模型提出计划、**经用户评审**后才能退出开工。

最关键的设计决定藏在这句注释里：

> Plan mode 是**软引导**；沙箱模式和批准策略各自强制执行限制，且不读写 plan 状态。

翻译：进入计划模式后，系统只是"劝"模型先想清楚别动手（通过提示词引导），但**并没有真的锁住工具**——真要限制动手，得靠沙箱模式（第 21 讲）和审批策略，而它们不关心 plan 状态的存在。为什么这么设计？因为**意图与强制的耦合是脆弱的**："计划模式=禁止一切写操作"听起来合理，但用户可能就是想在计划模式下做点只读实验。把"建议"和"禁令"分成两个正交开关，每种组合都合法。这是权限系统设计的重要一课：**宁可多给两个旋钮，不要做一个连体开关。**

## 二、todo：整体替换的艺术

第 06 讲精读过 TodoItem 类型和 todo/write 事件，现在看它的产品全貌。`packages/todo/` 的 README 强调它是**单一产品包**：

> 一个 agent 会话拥有该列表；不存在可替换的提供方约定。

对比 skill（下一讲的提供方注册表）或 subagent（多提供方矩阵），todo 刻意不做 seam。为什么？因为待办清单没有"换实现"的需求维度——它的价值恰恰在于**唯一性和简单性**：一个会话一份清单，`todo_write` 工具每次调用提交完整快照、整体替换、最后写入者胜。

回忆类型定义里那段注释的论证：没有 id、没有优先级——因为列表每次都被整个重写，条目不需要稳定身份；三态状态（pending/in_progress/completed）描述了模型和 UI 消费者需要的完整生命周期。**当某个设计显得过度复杂时，先问问它的数据是不是其实可以整体替换。**

UI 把这份清单渲染成实时任务面板——你看着智能体把 pending 逐个划成 completed 的过程，就是它工作透明度的直接来源。

## 三、goal：跨轮次的持久目标

todo 管"这一阵子干哪几件事"，goal 管"这场会话的根本目的"。`packages/goal/` README 的关键句：

> agent 会话的**持久目标状态**，独立于消费它的面向模型工具与续行策略。goal 状态是**所属会话日志的一部分**；消费方依赖 `dsh-goal`，**绝不依赖具体的 agent loop**。

三层信息量：状态住在日志里（重启不丢）；接口与消费者解耦（换循环实现不影响目标管理）；它与"续跑"（continuation）机制绑定——还记得第 06 讲 user/message 的三种来源吗？"entered goal continuation round"（目标续跑轮）就是第三种。目标驱动的续跑让智能体可以在长任务中断后自动接续，而不是靠人肉重新粘贴上下文。

## 四、强制力光谱：一张表收束

| 能力 | 数据形态 | 强制力 | 主要消费者 |
|---|---|---|---|
| plan | 按 agent 的协作状态事件 | **软引导**（提示词层面） | 模型 + 用户评审流 |
| todo | 整体替换的全量快照事件 | 无强制（纯记录） | UI 面板 + 模型自组织 |
| goal | 会话日志内的持久状态 | **续跑驱动**（影响轮次生成） | 续跑策略 + 模型 |

三者共享同一个底层事实：**状态即日志事件**——没有内存中的隐藏任务簿，一切可回放、可审计。差异只在数据的形状（快照 vs 状态）、消费者的身份、以及强制力的档位。

> 💡 **知识拓展：状态的"强制力光谱"**
> 给系统里的每个状态标注强制力是个好习惯：纯展示（todo 面板）→ 软引导（plan 提示词）→ 行为改变（goal 续跑）→ 硬禁止（沙箱）。混层是常见病灶：用纯展示的状态去硬禁止行为（用户改个配置就能绕过），或者用硬禁止去做本该软引导的事（用户失去自由度还不知道为什么）。画一条光谱，把你的每个状态钉上去，设计漏洞立刻现形。
