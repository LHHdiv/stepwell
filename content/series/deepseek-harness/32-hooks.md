卷七开篇。前六卷的扩展点都要写 TypeScript 插件，但世界上还有一大批用户的自动化资产是**shell 脚本形式的钩子**——尤其 Claude Code 和 Codex 的用户。`packages/hooks/` 的使命就是把这些存量资产接进来：把你的 `hooks.json` 指给桥接插件，原有的 shell 钩子在 dsh 里原样生效。

## 一、先立正统：什么是"规范拦截点"

README 开头先做了一次概念正本清源：

> 规范扩展接口本身是 **harness 的类型化拦截点**；「原生钩子」只是这些扩展点上的普通 Cordis 插件。

翻译一下这个宣言：dsh 并没有为"hooks"发明一套新机制——第 20 讲流水线里的 pre-execute 瀑布、第 13 讲的 agent/pre-step，这些类型化事件就是全部的拦截点。所谓"原生钩子"，就是监听这些事件的普通插件（有类型化返回值、没有序列化边界）。**hooks 子系统真正新增的只有一件事：把外部的 shell 钩子协议翻译到这些既有接口上。**

这个定位决定了包结构的三层：

| 包 | 职责 | 形态 |
|---|---|---|
| `hook-protocol/` | 方言无关的共享原语 | 库（不注册任何东西） |
| `hooks-claude-code/` | Claude Code 格式桥接 | 插件 |
| `hooks-codex/` | Codex 格式桥接 | 插件 |

## 二、共享库与方言桥的分界

hook-protocol 的 README 用一张表精确切分了"共同部分"与"方言部分"：

**共享库管**：matcher 匹配逻辑、退出码/stdout 编解码约定、通过 ctx.shell 执行命令、多个钩子的"最严格合并"策略、hook/invoked 与 hook/result 会话事件。

**各桥接管自己方言的形状**：CC 桥处理 CC 格式的逐事件 stdin payload、CC 的环境变量和 `${CLAUDE_PLUGIN_ROOT}` 占位符替换；Codex 桥处理 snake_case payload（带 turn_id/model 额外字段、不带尾随换行——细节抠到这种程度）以及它自己的 matcher 惯例。

这是**抽象泄漏治理**的标准作业：先把两个方言里真正同构的部分提炼成库（写一次测一次），每个桥只剩薄薄一层格式转换。判断哪些该进共享库的试金石很朴素——"这段逻辑换一个方言还成立吗？"

## 三、"有意的子集"：兼容工程的克制

Codex 桥的 README 坦白得像份合同：

> 该桥接实现 Codex 当前 hook 协议的一个**有意选取的子集**：10 个 hook 点中的 5 个（PreToolUse、PostToolUse、SessionStart、UserPromptSubmit、Stop）；仅使用正则的 matcher；没有 env 注入与占位符替换。

为什么敢只做一半？因为兼容层的价值在于**覆盖高频场景**，而不是复刻全部能力。五个 hook 点已经覆盖工具调用前后、会话起止、用户输入提交这些最高频的自动化节点；剩下的冷门点等真实需求来投票。而且 README 反复强调那句关键提醒："**所有定制行为都应当使用相同扩展点上的原生插件**"——桥接是给存量资产的迁移通道，不是新开发的首选路径。原生插件功能更强、类型安全、无序列化边界。

> 💡 **知识拓展：防腐层（Anti-Corruption Layer）**
> DDD 里的经典模式：当你的系统需要对接外部遗留系统时，在边界处放一层翻译，确保外部模型不会"腐蚀"内部设计。hooks 桥接正是教科书式防腐层：CC/Codex 的 payload 形状、退出码语义止步于桥内，进入 harness 后全是统一的类型化 Decision。判断你项目里是否需要防腐层的方法很简单：当你发现核心代码里出现了 if (externalFormat === 'cc') 这类分支时，就该抽了。

## 四、最严格合并

共享库里有个值得单独一提的策略："最严格合并"。同一个事件点上如果配了多个匹配的钩子（或桥接与原生监听者并存），决策取最严格者——任一 deny 即 deny，任一 ask 即询问。这延续了第 21 讲审批流的保守哲学：多道关卡之间是 AND 关系而非投票制。安全的裁量权从不做算术平均。
