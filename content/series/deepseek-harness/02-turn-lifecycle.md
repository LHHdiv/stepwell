先解释两个词，它们贯穿整个系列：

- **turn（回合）**：从你说一句话到智能体处理完毕，算一个回合。
- **step（步）**：一个回合内部，每次"请求模型 + 执行它要的工具"算一步。

一个 turn 可能包含多个 step。比如你问"帮我把这个文件里的错别字改掉"，模型可能第一步先读文件，第二步做修改，第三步汇报结果——三次模型请求，三个 step，同属一个 turn。

## 全程快进

现在你按下回车。下面是发生的事情（简化版）：

```
① 你输入的话被写入 session 日志          → user/message 事件
② turn 开始                              → turn/start 事件
③ agent-loop 领取输入，组装上下文：
   系统提示词 + 历史消息 + 可用工具清单
④ 发起对模型的流式请求                    → agent/request → llm/stream
⑤ 模型边生成边推流回来                   → assistant/chunk 事件（很多个）
⑥ 本步生成完成，完整回复入日志            → assistant/message 事件

⑦ 分支判断：模型想调用工具吗？
   ├─ 不想 → 回合结束                     → turn/end 事件
   └─ 想  → tool/call 事件
        ⑧ 工具执行前安全检查              → tools/pre-execute
        ⑨ 真正执行（读文件/跑命令…）       → tools/execute
        ⑩ 结果写回日志                    → tool/result 事件
        ⑪ 回到第③步，开始下一个 step
```

这就是 dsh 的心脏。所有其他部件——沙箱、压缩、子代理、审批——都是在这条流水线的某些站点上加装的"改装件"。

## 为什么工具之后还要再问一次模型？

初学者最容易困惑的是第⑪步：工具都执行完了，为什么还要再请求模型？

因为**模型不知道工具执行的结果是什么**。模型是"无状态"的：它每一步只看得到喂给它的消息列表。工具读出的文件内容、命令的输出，必须作为新消息进入日志，然后再请模型看一眼——它才能基于真实结果继续思考。

所以严格说，智能体的"智能"来自循环：

> **模型提议 → 工具执行 → 结果回流 → 再提议……直到模型认为任务完成。**

这个循环就是 `agent-loop` 包存在的全部意义。

## 事件溯源：日志是唯一事实来源

注意到上面每一步都伴随一个"事件"了吗？这不是巧合，而是 dsh 最重要的架构决策——**事件溯源（Event Sourcing）**：

- 对话历史不单独存储；`session` 包里只有一份**只追加的事件日志**（append-only log）；
- "模型应该看到什么"，是从这份日志**推导**出来的；
- 因此有一条铁律：**已入日志 = 模型可见**。任何没写进日志的东西，对模型而言不存在。

类比：医院病历。医生每次检查、用药、医嘱都按时间顺序记录在案。任何医生接手，翻病历就能完整了解病情——不需要"另存一份病情摘要"。dsh 的日志就是病历。
