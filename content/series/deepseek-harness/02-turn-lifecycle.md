在深入任何源码之前，我们先建立全系列最重要的一张心智模型：**一条消息的一生**。你在输入框敲下"帮我看看这个仓库的结构"并按下回车，到智能体开始流式输出答案之间，dsh 内部发生了一连串精确编排的动作。这一讲我们跟着官方架构文档里的流程图走一遍。看懂了它，后面 37 讲的每个零件你都知道该装回流程图的哪个位置。

## 一、两个时间单位：turn 与 step

先定义两个词，它们贯穿全系列：

- **step（步骤）= 一次模型请求 + 这次请求触发的所有工具调用。** 比如模型这次回复说"我需要先执行 `ls` 看看目录"，框架执行完工具、把结果喂回去——这算一个 step。
- **turn（轮）= 零个或多个 step 组成的一个完整工作单元。** 它在领取首条用户输入之前打开，在"不再欠任何工作"时关闭。

为什么要有两级？因为一个真实任务很少一步到位。"帮我看看仓库结构"可能是：step1 调 `ls` 工具 → step2 根据结果再调 `cat` 读 README → step3 组织语言回答。这三个 step 属于同一个 turn——**turn 是"办一件事"，step 是"其中一轮思考加动作"**。

还有个耐人寻味的细节：turn 可以包含**零个** step。如果一条输入刚被领取就被插件拒绝（比如触发敏感词过滤），dsh 仍会关闭一个不含 step 的 turn 并写进日志——"这次尝试"本身就是需要记录的事实。这种"宁可记录空转也不丢历史"的偏执，第 07 讲还会反复见到。

## 二、流程图：十个关键站点

下面是官方轮次流程（我在每一行加了中文注解）：

```text
turn/start                          # ① 轮开始：写一条持久的 turn 开始事件
  claim next-step input             # ② 从收件箱领取输入（可能附带排队消息）
  assemble prompt sections + tool schemas   # ③ 组装提示词片段 + 工具清单
  -> agent/pre-step                 # ④ 问监听者：这一步允许开始吗？
       step/start                   # ⑤ 步骤开始
       append entered messages as user/message  # ⑥ 输入落盘为持久日志
       derive model history from the log        # ⑦ 从日志投影出模型可见的历史
       agent/request -> llm/stream -> assistant/chunk* -> assistant/message
                # ⑧ 发起流式请求；每个碎片实时入日志；最后完整回复入日志
       tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
                # ⑨ 有工具调用就走工具流水线：前置检查→执行→后置处理→结果落盘
       step/end                     # ⑩ 步骤结束
     还有活干？-> 回到 ② 开下一个 step
  -> agent/turn-stopping            # 收尾检查点（串行事件）
turn/end                            # 轮结束：写一条持久事件
```

几个值得停下来咀嚼的地方：

**第 ④ 站是权力的分水岭。** `agent/pre-step` 决定"模型能看到什么"：监听者可以改写已领取的消息（比如注入额外上下文），也可以直接拒绝。这是 dsh 实现权限控制、上下文注入、消息改写的统一入口。

**第 ⑥⑦ 两站藏着 dsh 的世界观：模型可见即已记录。** 注意顺序——先把输入写成持久日志事件，再从日志"投影"出要发给模型的历史。不是"发出去顺便记一笔"，而是"只有记下来的才有资格被发送"。这条铁律保证会话可以随时断电重启、从日志完整重建，第 08 讲拆它的实现。

**第 ⑧ 站解释了你看到的打字机效果。** 模型的回复是一个个 chunk（碎片）流回来的，每个碎片实时写入日志（`assistant/chunk*`），全部到齐后再写一条完整的 `assistant/message`。原始碎片的保留保证了 UI 回放的绝对保真。

**第 ⑨ 站是循环得以成为循环的关键。** 工具执行的结果会作为新输入回到第 ② 站——只要模型还想用工具（"tools owe another request"，工具欠着下一次请求），循环就继续；直到模型给出纯文本回复且没有新输入，turn 才在第 ⑪ 站关闭。

> 💡 **知识拓展：这就是 ReAct 模式的工程化**
> 学术界把"推理(Reason)→行动(Act)→观察(Observe)→再推理"的循环叫 ReAct。dsh 的 turn/step 就是它的工业级实现：第③-⑧站是 Reason，第⑨站是 Act+Observe，回到②是再 Reason。你在别的框架里见到的"agent 循环""tool use loop"，都是这套流程的变体——以后你看任何一个 Agent 产品，都可以问一句："你的 pre-step 在哪？你的日志铁律是什么？"

## 三、三种事件域：同一套系统里住着三种"广播"

流程图里出现了很多 `xxx/yyy` 形式的名字，它们都是**事件**。但 dsh 把事件分成三个域，用途截然不同：

| 域 | 例子 | 寿命 | 用途 |
|---|---|---|---|
| **会话事件** | `user/message`、`assistant/message`、`tool/result`、`turn/*` | 持久化到磁盘 | "发生过什么"的事实，重启后可回放 |
| **Agent 事件** | `agent/pre-step`、`agent/request`、`agent/turn-stopping` | 只存在于运行中 | 观察、拦截、改写进行中的工作 |
| **能力事件** | `fs/*`、`tools/*`、`telemetry/*` | 只存在于运行中 | 给某项能力附加策略或适配器 |

判断标准一句话：**这个事实需要在重新加载后依然存在吗？** 需要，就做成会话事件；只是想实时插手，就用 agent 或能力事件。选对事件域，是给 dsh 添加新行为时的第一个决定（官方文档原话）。

## 四、waterfall：必须喊"next()"的接力赛

注意流程图里 `agent/pre-step`、`agent/request`、`llm/stream` 和三个 `tools/*` 事件旁边标注的性质——它们是 **waterfall（瀑布式）事件**。这类事件的监听者排成一列，每个人收到事件时还收到一个 `next()` 函数：

- 你处理完自己的逻辑后**必须调用 `next()`**，接力棒才会传给下一位；
- 你也可以**不调 `next()` 直接返回**——这叫短路，意味着你否决了这次操作（比如审批插件拒绝执行危险命令）；
- 返回值可以层层包装，像洋葱一样由外向内再由内向外。

而 `agent/turn-stopping` 是 **serial（串行）事件**：依次执行、没有 `next()`、收集每个人的意见。为什么它是 serial？因为它在做最终裁决——"轮次可以停了吗？"——这种一锤定音的事不适合洋葱模型。

这两种模式的细节和源码实现，第 03 讲讲 Cordis 时展开。现在记住直觉即可：**观察者用 emit，把关者用 waterfall，裁决者用 serial**。

## 试一试

启动任意一个 AI 编程智能体（不一定是 dsh），给它一个需要多步的任务，比如"看看当前目录有什么文件，然后告诉我哪个最大"。数一数它内部发生了几轮"请求模型→执行工具"？每多一轮，就是一个新的 step——你现在已经在用本讲的词汇解剖产品了。
