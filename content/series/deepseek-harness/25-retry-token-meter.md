模型 API 是整个系统里最不可靠的邻居：限流、超时、抽风返回空内容……第 23 讲把错误分类好了，本讲看两件后续大事：**错了怎么办（llm-retry）**和**花了多少怎么知道（token-meter）**。两个包都不长，但设计密度极高。

## 一、重试挂在哪里：一个架构决定

llm-retry README 开头就亮明立场：

> 它不包装 ctx.llm.stream()：每次适配器调用仍是一次提供方尝试，**每次重试都会开启新的编号轮次**。

回忆第 14 讲：请求失败后主循环走 agent/request-error 瀑布，监听者裁决 retry 则 continue 回到循环开头——重试发生在 step 内循环层，而不是把 stream 调用包一层自动重试的壳。两种方案的区别是深刻的：

- 包装式（常见库的做法）：重试对外完全隐形，调用方毫无感知；
- **dsh 的瀑布式**：每次重试都是主循环的一次真实迭代——新开编号轮次、重新走 buildRequest、重新从日志推导历史。

为什么选后者？因为**重试必须留下痕迹并接受约束**：取消信号要能打断退避等待、日志要记录每次尝试、策略变更要能生效。隐形重试是调试噩梦（"这请求到底发了几次？"），而显式重试让系统对自己的行为全知全觉。

## 二、两种模式：normal 与 always

**normal mode（默认）**：只对五类"安全可重复"的错误重试——EMPTY_RESPONSE、RATE_LIMIT、SERVER、TIMEOUT、TRANSPORT，最多 5 次，指数退避从 500ms 到 10s 封顶，外加 10% 抖动。注意 EMPTY_RESPONSE 的注释解释："适配器对未产生任何持久内容的退化完成所作的分类，因此**可安全重复**"——重试的安全性取决于操作是否幂等，空响应意味着什么都没发生，重来无副作用。这个清单本身就是一份"哪些错误值得再试"的教学大纲。

**always mode**："先请求下游恢复，再无次数上限地重试每个模型请求失败"。成功、用户取消或插件卸载才终止。这是给"宁可等到天荒地老也要完成任务"的场景准备的批处理模式。

两者共享退避算法，还有两个精修细节：

- **对称抖动（jitter）**：10% 随机偏移防止"惊群"——一千个客户端同时被限流、同时精确地 5 秒后重试，服务器刚缓过来又被踩塌。抖动把重试时间打散成一片；
- **尊重服务器的 Retry-After**：有效 providerRetryAfterMs 不超过本地上限时直接采用且不加抖动——服务器亲口说的等待时间比本地猜测更准；超过上限时 normal 继续委托、always 改用本地退避，避免那条指令变成无限期停摆。

## 三、重试也要记账

每次重试周期在日志里留下两类 log-only 事件：

- **llm/retry**（进入等待前）：携带共享 retryId、提供方、mode、解析后策略的规范 key、失败详情、计划延迟。UI 渲染"∞"或有限次数就靠它；
- **llm/retry-started**(真正开始重试前)：同样的 retryId 加轮次步骤编号。退避期间被取消则不会写它——没发生的事不留痕。

最讲究的是**延续编号的判定规则**：只有"提供方相同且完整策略 key 相同"的事件才延续同一个 retryId 计数；换了路由或改了策略配置，重试历史从零开始。为什么？因为重试次数的语义绑定在具体策略上——换了策略还沿用旧计数，"最多 5 次"就名存实亡。规范 key 甚至对 normal 的 code 列表做了排序（因为合格性是集合判断，顺序无关）——**连 key 的规范化都为语义正确性服务**。

## 四、token-meter：给整栋楼装电表

`ctx.tokenMeter` 单例服务的定位一句话："具备**回放感知能力**的 token 测量，从持久日志为每个会话推进一个隔离 fold"。

拆解三个关键词：

- **从日志推进**：计量不是在发送请求时顺手累加内存变量，而是把日志里的用量事实（assistant/message 的 usage 字段，第 06 讲）当作唯一来源做折算(fold)。重启、fork、恢复——只要日志在，计量就在；
- **隔离 fold**：每个会话独立的计算通道，互不污染；
- **共享**：压缩策略要知道当前压力、计费报表要用总量——大家读的是同一份从日志推导出的真相，不需要各记各的账。

它的估算器也很有性格："有意使用一项固定启发式：每 token 按四字符估算"，并且**拒绝任何配置键**。注释给出的理由值得背下来："模型容量属于拥有精确路由的适配器"——粗估归 meter（够压缩策略用了），精算归适配器（它们知道确切的 tokenizer）。**把模糊的工具放在该模糊的位置，拒绝让它假装精确。**

> 💡 **知识拓展：指数退避的三要素**
> 本讲的退避算法是分布式系统的标准配方：**基数**（500ms 起）、**倍率**（逐次翻倍到上限 10s 封顶）、**抖动**（±10% 打散重试时间）。再加一条礼仪：**尊重 Retry-After**。任何需要访问有限资源（API、数据库、文件锁）的重试逻辑都逃不开这四件事。写的时候问自己：我的操作幂等吗？我的上限是多少？我和同伴们会不会挤在同一天桥上？
