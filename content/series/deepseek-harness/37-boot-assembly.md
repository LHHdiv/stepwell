卷八开篇：产品形态。前七卷拆的是发动机和零件，现在看整车下线的最后工序——**装配与交付**。第 04 讲我们从用户视角看过四层叠加，本讲钻进 `packages/boot/` 看它的代码实现。

## 一、cmdline：分权到极致的命令行

你输入 `dsh --profile web chat --model deepseek-chat "你好"`，谁来解析这串东西？boot/cmdline 的 README 给出了一个教科书级的分权答案：

> 启动器只解析属于自己的 flag（`--profile`、`--patch`、配置 dump），并把**其后的一切原样交给配置树**，因此 **flag 家族、`--help` 文本和解析错误都由应用自己持有**，启动器不必知道它们。

细品这个设计的妙处。传统做法是中央命令行解析器注册全部子命令的参数表——每加一个功能都要动启动器，启动器成了全系统的依赖热点（也是合并冲突的重灾区）。dsh 反过来：启动器只认识三五个属于自己的全局 flag，遇到第一个陌生 token 就停手，剩下的整串交给配置树里挂载的应用去解析。

收益清单：子命令可以来自任何插件（它们的 --help 自己写、错误自己报）；启动器永远稳定不需要跟着功能迭代；测试时每个应用测自己的 CLI 契约。**把"认识的少"变成一种架构优点。**

## 二、app-boot：单点负责纪律

第二个包 app-boot 解决另一个常见病：多个可执行入口各自实现启动逻辑，久而久之行为分化——A 入口对配置错误的报错带颜色、B 入口的退出码是 1 而 C 是 3。

> 供 app bin 共用的启动粘合层：每个 bin 都是在这些辅助函数之上构建的精简自执行组合……这样，**Loader 故障行为只由一处负责，不会在已发布产物之间逐渐分化**。

"逐渐分化"（drift）是大型 monorepo 的慢性病：没有谁故意写不一致的代码，只是每次小改动都引入一点点偏差，三年后没人能解释为什么两个入口行为不同。药方就是本包的实践：把启动的关键语义（尤其失败路径）收拢到一个共享层，bin 本体瘦成几行组装代码。dsh 主 CLI 和 acp-demo 这两个风马牛不相及的产品共用它——差异被显式参数化（诊断前缀），共性被强制复用。

## 三、入口的极简主义

apps/cli 的 README 描摹了最终形态：

> [`src/args.ts`] 负责命令语法，[`src/bin.ts`] 只加载选中的运行器。无效命令、来自其他模式的选项、配置错误和启动失败都会以非零状态退出。

整个主入口包就干两件事：定义命令语法、按选择加载 runner。连"无效命令怎么处理"都只有一句话的政策——非零退出码，不废话。对照第 04 讲跑起来的体验（npx 一条命令进浏览器），你现在知道那份丝滑背后是三层结构在托举：bin（薄壳）→ app-boot(粘合) → 配置树（真正的应用）。

## 四、四层叠加的实现落点

最后把第 04 讲那张千层饼映射到源码位置，完成闭环：

| 叠加层 | 内容 | 实现锚点 |
|---|---|---|
| bundle 按序 | dsh-base → dsh-web-app / dsh-headless | packages/bundle/ 各组合包 |
| profile patch | profile 自带的 cordis.patch.yml | Harness home 的具名组装 |
| home patch | 用户全局覆盖 | $DSH_HOME 下的 patch 文件 |
| --patch overlay | 命令行临时补丁 | cmdline 解析的 flag |

而 preset（第 36 讲）作为第五种力量挂在 agent scope 层面参与其中——装配不是一次性的开机仪式，而是从进程级一路细化到会话级的连续光谱。

> 💡 **知识拓展：启动流程的"洋葱测试"**
> 检验一个系统启动设计的好坏，可以用三个问题当探针：①加一个新子命令要改几处？（理想：一处，且不在公共层）②两个入口的行为差异能被解释吗？（理想：全部差异都有显式来源）③配置错误发生在第几层被发现？（理想：离原因最近的层）。用这三问审视你自己的项目 main 函数，通常五分钟内就能找到改善点。
