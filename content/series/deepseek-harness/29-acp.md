第 27、28 讲都是"把别人的能力接进来"。本讲反个方向：**把 dsh 的智能体暴露出去**，让别的程序也能驱动它。这就是 ACP（Agent Client Protocol，智能体客户端协议）的使命。

## 一、ACP 是什么

想象几个场景：你的 CI 流水线想调用智能体检代码；你的团队机器人想让智能体回答问题；你写的脚本想把"让 AI 干活"当成一个普通命令用。这些场景的共同点是：**驱动者不是人，而是另一个程序**。它们需要一个标准的对话接口——问它、发任务、收结果、看进度。ACP 就是这个标准。

dsh 的 `packages/acp/` 一页 README 说清了全部定位：

> ACP 组通过该协议将 harness 中的 agent **公开给程序化客户端**。它是**互操作传输层**，不是展示或人机交互层。

两个关键词都要咬文嚼字：

**"公开给程序化客户端"**——方向是出站服务：dsh 扮演服务器，外部程序扮演客户端。这与 MCP（dsh 扮客户端用别人的工具）恰好互补，一进一出构成完整的互操作版图。

**"传输层不是展示层"**——ACP 关心的是会话建立、消息传递、状态同步这类"怎么可靠地对话"；至于客户端拿到结果后渲染成聊天气泡还是终端文本还是仪表盘，协议一概不管。类比 HTTP 与浏览器的关系：HTTP 不规定网页长什么样。这条边界让 ACP 能同时服务于 IDE 插件、聊天机器人、CLI 工具——各家用各自的皮。

## 二、双生结构：一个协议，两端两包

README 里有一句容易被略过但组织上极重要的注解：

> 配对的进程外 subagent *客户端*在 [`subagent/subagent-acp`]，因为它实现的是 subagent 提供方接口。

画出来更清楚：

```text
        ACP 协议（同一种语言）
   ┌────────────┬────────────┐
   ▼                         ▼
packages/acp/          packages/subagent/
acp 服务器              subagent-acp 客户端
（把 dsh 智能体           （把【别的产品】的
 暴露给外部程序）          ACP 智能体当自己的子代理）
```

同一个协议，dsh 同时实现了它的**两端**：作为服务器对外输出自家智能体的能力；作为客户端把外部的 ACP 智能体接入 ctx.subagents 当子代理使唤。而这两端之所以不住在一个包里，是因为它们各自实现的是**完全不同的内部接口**（前者面向 agent 服务暴露，后者面向 subagent 提供方注册）——按依赖方向分包，而不是按"用了同一协议"这种表面共性分包。这是 monorepo 包切分的教科书案例。

## 三、"仅面向自动化"的取舍

注意 acp 包的自我限定："**仅面向自动化的** ACP 服务器"。它不试图成为人类用户的主界面——那是 client TUI 和 web 前端（卷八）的领地。为什么砍掉交互功能？因为自动化客户端的需求和人机界面的需求差异巨大：脚本不需要富文本卡片、不需要审批弹窗的人性化设计、不需要打字机动效；它需要的是稳定、可预期、机器友好的语义。为一个协议同时伺候两类主顾，只会两头都做不好。**识别你的第一受众，然后勇敢地不做另一半。**

## 四、协议生态中的 dsh 全景

至此卷六的协议拼图凑齐了大半，站在高处看一眼 dsh 的互操作姿态：

```text
            ┌── MCP 客户端 ──→ 外部工具服务器（接进来）
  dsh 智能体 ┼── LSP 客户端 ──→ 语言服务器（接进来）
            ├── ACP 服务器 ←── 外部程序（暴露出去）
            └── subagent 客户端 → Claude Code / Codex / 其他 ACP 智能体（纳编进来）
```

四个方向、四种姿态，每种都用最小的包面积实现。现代软件的竞争力越来越不在"我有什么"，而在"我能和什么对话"——dsh 的 packages 目录就是这份竞争力的清单。

> 💡 **知识拓展：协议设计的"薄"哲学**
> 对比三种协议的厚度：MCP 定义了工具、资源、提示词等丰富原语；LSP 有上百种请求方法；ACP 却刻意做薄——只管会话与消息。厚度没有高下，取决于**变异维度**：MCP 面对的是千变万化的工具形态，必须厚；ACP 的两端（智能体和自动化客户端）内部结构已经各自稳定，只需约定交换格式，薄即是美。协议该多厚？数数你需要约束多少种变异。
