第 33 讲的任务管理都在"对话内"，本讲的三个家族处理"对话外"：任务跑得久（jobs）、事情在未来（schedule）、一次要派很多（workflow）。三者共同回答一个难题：**当对话暂停时，后台的工作怎么办？**

## 一、jobs：长任务的登记处

一个工具要跑十分钟（大型测试套件、批量转换），模型干等吗？dsh 的答案是把长任务**后台化**：立刻返回一个任务 id，模型继续干别的，稍后用工具查询进度或收取结果。

`packages/jobs/` 家族三层结构：

- **jobs/**：抽象注册表约定 `ctx.jobs`。最妙的设计是 `JobKindMap`——生产方插件用它自己的不透明 id namespace **扩展**这个映射。翻译：任务种类是开放词汇！terminal 后台发送注册一种 kind、未来的构建系统注册另一种，注册表的语义随声明合并生长（第 06 讲 TurnEndReasonMap 的同款手法）；
- **jobs-local/**：进程本地实现。注意它的输出纪律："只交出全新快照，从不交出实时状态"——调用方拿到的是冻结副本，想看新进展就再查一次。杜绝了"拿着内部对象的引用把人家的状态改乱了"这类事故；
- **tool-jobs/**：面向模型的三个控制器工具（按 kind 无关的方式观察/取消/等待）+ 完成通知 + 一个后台工作提示词区段。

还有两条纪律贯穿约定：**owner 隔离**（每个任务有所有者，别人的任务你不能乱取消——和 PTY 会话归属同一哲学）与**共享 id**（`<kind>-N` 形式的可读编号）。

## 二、schedule：活在日志里的闹钟

schedule 家族管理提醒，它有两个设计决定值得细品：

**第一，提醒状态存在哪？"进程内 owner 只会在该 Session 拥有 live 根 Agent 时等待"——持久状态保存在原 Session 日志中。** 定时器本身是可丢弃的投影：进程重启，内存里的 timer 全没了？没关系，日志里的提醒事实还在；"cold Session 再次 live 后会恢复**逾期工作**"。你三天前设的提醒，机器关机两天，开机后智能体复活时会把逾期的提醒补给你。又是仅追加日志的红利：状态即事实，事实即可重建。

**第二，诚实的边界声明**："这不意味着存在外部通知渠道。"提醒只在会话活着时于会话内触发——它不会给你的手机推通知。README 把这个限制写在脸上，避免用户产生错误期待。**功能边界写得越清楚的产品越可信。**

版本 1 的参数也透露着保守：延时用正的安全整数秒、间隔至少 5 分钟固定速率。先不做花哨的 cron 表达式，把最小可用做扎实。

## 三、workflow：模型给自己写流水线

三个兄弟里最有想象力的是 workflow。`tool-workflow` 的 README 一句话：

> 运行一段**扇出 subagent 的 JavaScript 编排脚本**，并返回脚本的最终值。

使用场景：主智能体面对一个大任务——"把这二十个模块各自审查一遍再汇总"。逐个串行太慢、一次性全塞上下文装不下。workflow 让模型**现场写一段 JS**：循环生成子代理请求、Promise.all 控制并发、汇总各路结果——脚本提交给 ctx.workflowEngine 执行，引擎在 seam 之后负责解析、执行、上限与取消。

注意安全边界的划分："将**通用工具**与**固定策略工具**公开给模型"——编排脚本驱动的子代理可以拿到通用工具集，但策略类工具（审批等）由引擎固定，不给脚本篡改的机会。脚本能决定"派多少个兵、怎么分工"，不能决定"绕过安检"。加上执行上限（防止模型写出死循环烧钱），这套机制在灵活性与可控性之间找到了支点。

这是"代码即编排"路线的典型落地：与其发明一套 DSL 或 YAML 流程语言让模型学习，不如直接让它写最通用的语言（JS），引擎负责沙箱化的运行时。

> 💡 **知识拓展：前台-后台的边界设计**
> 对比三兄弟的"后台程度"：jobs 是**会话内的异步**（对话继续，任务并行）；schedule 是**跨时间的持久**（人走了，事还在账上）；workflow 是**单次调用的扇出**（一步之内并行多个子世界）。给后台能力分类时问三个问题：谁在等结果？结果何时需要？生命周期多长？三问答完，该选哪个家族自然浮现——大多数"要不要加个消息队列"式的设计争论，源于没先回答这三问。
