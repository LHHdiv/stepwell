卷四收官。前面讲了工具怎么定义、调用怎么流转、危险怎么设防，本讲看最底层的那块土地：**一切执行最终发生在哪**。dsh 把这块土地切成四个接缝：subprocess（孵化器）、shell（命令后端）、terminals(持久终端）、fs(文件世界）。它们的共同点：全部是能力 seam，全部可整套替换——把这几个 Provider 指向远程机器，智能体就整体"搬家"了（第 21 讲结尾说的"换器官"）。

## 一、subprocess：唯一的孵化口

所有新进程都从 `ctx.subprocess` 出来。这个收口的意义在安全上是一目了然的：**想审计"系统里跑过什么进程"，盯住一个接缝就够了**。第 19 讲的 terminal-bash 注释里出现过它的名字——`ctx.subprocess.spawnTerminal`，连持久终端也是站在它肩上的。

分层图：

```text
   工具层      bash 工具 · terminal 六件套 · code-runtime
                │ 只认识
   能力层      ctx.shell（命令后端）    ctx.terminals（会话注册表）
                │ 都经由                    │
   孵化层      ctx.subprocess.spawn / spawnTerminal
                │ 最终
   操作系统     你的机器（或被整体替换的远程世界）
```

工具不碰 subprocess，能力不直接 fork——每层只认识下一层的接口。想给所有进程统一加个记账？改一处即可。

## 二、shell：一次性的命令执行

`ctx.shell` 的后端矩阵在第 19 讲见过：bash-local / bash-sandbox / pwsh-local / pwsh-sandbox。它的心智模型是**一锤子买卖**：每次调用 = 新起进程 → 跑完 → 收输出 → 进程销毁。状态不保留（环境变量、当前目录、后台任务统统随进程火化），换来的是完全的可预测性与可沙箱性。

bash-sandbox 这个后端的名字里藏着它的实现：它就是 bash-local 加了一步——spawn 前先过 `ctx.sandbox.confine(argv, policy)`（第 21 讲）。**安全不是独立产品，而是后端的组合方式。**

什么时候一锤子不够用？启动 dev server（要活着）、交互式程序（要持续喂输入）、多步调试（要记住上下文）——这就轮到下一层。

## 三、terminal：持久的 PTY 会话

PTY（伪终端，Pseudo-Terminal）是操作系统提供的"假终端"抽象——你的 IDE 内嵌终端、SSH 会话都是它。dsh 的 terminal 家族（第 19 讲的表格）围绕三个概念：

1. **会话有品牌化 id 且归属精确的 Agent**——子代理不能摸主代理的终端；
2. **发送-就绪检测**：向终端发命令后如何知道"跑完了"？后端实现了就绪探测（等提示符回归之类），这是自动化驱动交互式程序的核心难题；
3. **有界状态**：只留最近 N 行滚动窗口，长跑进程不会撑爆历史。

六个面向模型的工具覆盖完整生命周期：创建、发送输入、读输出、等待就绪、列出会话、关闭。与 bash 工具的选择题就此清晰：**要结果选 bash，要过程选 PTY**。

## 四、fs：文件世界的四件套

```text
packages/fs/
├── fs                  # Service Definition：ctx.fs 接缝词汇
├── fs-local            # Service Provider：本地文件系统的实现
├── fs-observation-policy # 观察策略：哪些文件变动该通知模型
└── fs-sandbox          # 受限文件系统视角（配合沙箱模式）
```

最有味道的是后两个。**fs-sandbox** 是"沙箱模式的文件视图"：read-only 模式下模型看到的是一个只读的世界观——不是每次操作去检查权限，而是提供方本身就不具备写能力。**让违规不可能发生，好过让违规被发现。**

**observation-policy** 处理另一个问题：文件系统那么大，哪些变化值得告诉模型？你编辑器保存了一个文件，智能体应该知道（它可能正拿着旧内容干活）；node_modules 里蹦出一个缓存文件，就不用打扰了。观察策略就是这道过滤器，筛出的事件经 agent.inject()（ wakeup=false 那个！）进入 next-step 队列——第 17 讲的机制在此服役："文件变更通知"正是官方注释列举的 inject 用例第一名。

而写路径上的 **fs/write-intent 意图门控**（第 20 讲流水线第⑧站）：tool-fs 动手改文件前先广播意图事件，策略监听者可以放行也可以拦截。**宣布在先，行动在后**——审计和拦截都有了着力点。

> 💡 **知识拓展：为什么"执行世界"要整体可替换？**
> 回想第 03 讲能力 seam 图谱里那句论断："文件系统与进程提供方共享同一个执行世界，把它们指向远程沙箱，也就把 Bash、PTY 和 LSP 一并搬了过去。"这就是卷四反复出现的"换器官"：本地执行和云端执行的区别不在某个工具，而在整片土地。设计扩展体系时，先识别哪些能力是"命运共同体"（共享同一物理底座），再把它们编成同一个替换单元——切分错了粒度，扩展时就会四处漏水。
