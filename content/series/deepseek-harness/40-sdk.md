卷八收官。前面所有入口（web 界面、ACP）都面向"使用智能体"，本讲的 sdk 面向更深的诉求：**把 harness 运行时当成你程序里的一个组件来编程**。用官方的话说："用于从另一进程驱动 Harness 运行时的协议栈。"

## 一、家族成员与分层

```text
packages/sdk/
├── protocol/    # 纯库：wire format——换行分帧 JSON-RPC 2.0 + 具名类型
├── server/      # dsh-sdk-jsonrpc-server 插件（跑在 harness 内侧）
└── client/      # TypeScript 客户端（跑在你的进程里）
python/          # Python SDK（顶层目录，复现协议结构）
```

分层纪律严明：**protocol 是纯库**——"无插件、无 Config、无注册"，只有两样东西：一个按换行符分帧的 JSON-RPC 2.0 传输类，加上协议两端共同使用的具名请求、结果与通知类型。"包根枚举协议消费方接口；源模块不支持深层导入"——公共面收敛在包根，防止消费者依赖内部实现细节。

服务端是插件（jsonrpc 通过 stdio 对外服务），客户端是库——同一份协议，两侧形态各自归位。

## 二、"三不做"边界

README 开头的边界宣言比功能列表更重要：

> 调用方提供运行时可执行文件及其 cordis.yml；本组**不创建、不配置、不构建或启动**开发者项目。

翻译成产品语言：SDK 负责"对话通道"，不负责"项目脚手架"。它不会帮你初始化工程、不会生成配置模板、不会替你启动子进程——这些它统统不做，文档还专门有一条"工具链移除"决策记录解释为什么砍掉了原本的工具链功能。

这个决定的价值在于**定位纯粹性**。一旦 SDK 开始管"怎么建项目"，它就得押注某一种项目形态（哪个包管理器？什么目录结构？），然后随生态演化背上无穷的兼容包袱。只做协议栈，任何语言、任何构建体系、任何宿主环境只要能起一个进程读写 stdio 就能接入——Python SDK 的存在就是证明。

## 三、JSON-RPC over stdio：最朴素的可靠选择

协议选型也透着务实："以换行符分隔的 JSON-RPC"。逐项拆：

- **JSON-RPC 2.0**：二十年历史的规范，请求/响应/通知三种消息语义齐备，错误码约定成熟。没有发明新东西；
- **stdio 传输**：进程的标准输入输出是世界上最通用的 IPC——不需要端口分配、不需要握手认证框架（进程本身就是信任边界）、天然适配容器和沙箱；
- **换行分帧**：每条消息一行 JSON。相比带长度前缀的二进制帧或复杂的 multipart，换行分帧让人可以用任何语言、甚至 cat 和 grep 调试协议。

对比第 38 讲的 Typert RPC（浏览器 ↔ 宿主，要身份解析和双向校验），SDK 的 JSON-RPC（外部程序 ↔ harness）选了最薄的一层。同一个仓库里两种 RPC 共存且各得其所——**按边界的信任模型选协议厚度**，又一次得到验证。

## 四、Python SDK 的"复现"哲学

家族页里有个细节耐人寻味：Python SDK "**复现这些结构但不导入它们**"。明明可以生成代码共享类型，为什么要手写一份平行实现？

因为跨语言的类型共享是一张长期饭票变长期枷锁：代码生成要求两端锁死同一套工具链版本、同步发版、处理生成产物的语言习惯适配。而协议本身已经是具名类型的 JSON——它是天然的稳定契约，Python 侧照着写反而自由：不受 TS 工具链牵制、可以用 Python 地道的 API 设计。代价是两端可能漂移，但协议测试（contract 测试）兜住了语义一致性。**小协议值得复现，大协议才需要生成**——这是跨语言 SDK 的选型标尺。
