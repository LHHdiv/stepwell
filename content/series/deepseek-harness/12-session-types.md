前两讲我们认识了词汇表里的每一个词。但一套语言光有词不够，还需要**语法和宪法**——什么能写、按什么格式写、遇到读不懂的话怎么办。`core/session/src/types.ts` 里除了事件定义，还藏着三块"宪章文本"：格式版本号、会话头部、以及一个不起眼的布尔字段 `ignorable`。它们合起来回答一个大问题：**一条永不回头、越写越长的日志，怎么保证十年后还能被正确地读出来？**

## 一、为什么是"仅追加"

先复习这个根本设定：会话日志**只允许追加，不允许修改或删除**。要"改变"历史？追加一条新事件来表达（比如压缩时用带 replace 标记的新节点覆盖旧内容——第 13 讲细讲）。原始记录永远躺在那里。

这个约束换来四样东西：

1. **可审计**：发生过的事无法被篡改，排查问题有完整时间线；
2. **可回放**：从头重放日志就能重建任意时刻的状态——UI 回放、fork 分叉、断点续跑全都吃这条红利；
3. **崩溃安全**：追加到一半断电，最坏情况是最后半条不完整，之前的完好无损；如果是原地改写，损坏的可能是一大片；
4. **并发友好**：多读者永远看到一致的已提交前缀，不需要锁。

代价也很直白：日志只增不减，磁盘占用持续增长。dsh 用压缩（compaction，第 24 讲）和外溢存储（spill）来对冲。这是典型的工程交换：**用空间和纪律，买正确性和可追溯性**。

> 💡 **知识拓展：这个思想在业界到处都是**
> - 数据库的 WAL（预写日志）：先记日志再改数据，崩溃后靠日志恢复；
> - Kafka：消息队列本身就是仅追加日志，消费者各自维护游标；
> - Event Sourcing（事件溯源）架构：不存"当前状态"，只存"发生的事件"，状态随时重放得出——dsh 的会话正是这个模式的标准实现；
> - 甚至区块链的本质也是仅追加 + 哈希链。
> 认出这些亲戚后你会发现：dsh 不是发明了什么，而是把久经考验的模式用在了智能体这个新领域。

## 二、SessionHeader：日志之外的"户口本"

每个会话有一份**不进事件日志**的元数据，源码叫 SessionHeader：

```ts
export interface SessionHeader {
  readonly version: number        // 磁盘格式版本，创建时盖戳
  readonly id: SessionId          // 会话 ID（第 10 讲的品牌类型）
  readonly createdAt: number      // 创建时间的 Unix 毫秒数
  readonly cwd?: string           // 创建时的工作目录（绝对路径）
  readonly parentSession?: SessionId  // fork 自哪个父会话（种子血统）
  readonly seedLength?: number    // 通过种子继承了多少条前置事件
  readonly origin?: 'subagent'    // 粗粒度产品分类：子智能体出身
  readonly delegationDepth?: number   // 委派深度：顶级缺省，子代理=父+1
  readonly agentPreset?: string   // 由哪个 agent 预设组装而成
}
```

三个字段值得停下来：

- **`delegationDepth` 为什么持久化？** 注释说得很清楚：如果只在运行时内存里记深度，子代理重启恢复后就"忘了自己是几代"，递归预算（防止无限套娃）就形同虚设。**凡是重启后会改变行为的，都必须落盘**。
- **`agentPreset` 同理**：预设决定了会话拥有哪些工具和提示词。如果恢复时用了不同组合，模型面对的是它"历史上用过的工具如今不存在"的鬼故事。把预设名存进头部，就是给未来恢复时的行为一致性上保险。
- **`seedLength`**：区分"继承自父会话的前缀"和"本会话自己的工作"。没有它，resume 和 replay 无法分清哪些是遗产、哪些是奋斗。

注意所有字段都是 `readonly`，注释称它是 "Immutable validated storage metadata"（不可变的已校验存储元数据）。户口本一旦签发不改，改了也不算数。

## 三、版本号：写入者说了算

```ts
/**
 * 磁盘会话格式的版本号……单一的单调递增整数，不分主次版本。
 * 是否需要升版，由写入者产出什么决定，而不是较新的读取者能接受什么：
 * 当且仅当旧运行时再也无法完整正确地处理新日志时才升版。
 */
export const SESSION_FORMAT_VERSION = 0
```

这段注释是我心目中全仓库最精彩的设计文档之一。它确立了一条反直觉的原则：**版本的裁决者是写入端，不是读取端**。

直觉上你可能觉得"新版程序能读旧格式就行了吧？"——但注释点破了陷阱："parses without error is not correctness"（解析不报错 ≠ 正确）。假设新格式给某事件加了个影响重建的字段，旧运行时照样能把它 JSON.parse 出来，然后**静默地忽略那个字段、错误地重建会话**——没有任何报错，但结果是错的。这比崩溃糟糕十倍。

所以规则是：只要旧运行时会"读错而不自知"，就必须升版本号，让旧运行时当场拒绝并明说"我读不了"。同时注释也给了刹车——**普通新增事件类型不算结构变更，不许升版**（否则每次加点小功能全世界都得迁移）。那普通增长靠什么兼容？靠下一节的机制。

当前版本钉在 0，注释坦白说：harness 未发布期间不承诺任何兼容性，不提供迁移。诚实的契约好过含糊的承诺。

> 💡 **知识拓展：容错性设计里的两个流派**
> - **Postel 法则**（对自己发的保守，对他人的接受的宽容）：网络协议常用，尽量容忍输入的不完美。
> - **Fail loud**（大声失败）：遇到不理解的东西立即拒绝，绝不猜。dsh 在日志格式上坚定选了后者。选择依据是**错误的代价**：网页容错一下顶多排版歪，而会话日志静默错读意味着用户的全部对话历史被曲解——数据完整性场景，宽容就是犯罪。

## 四、ignorable：一枚布尔值的哲学

普通的事件类型增长，靠每个事件上的可选标记 `ignorable` 来消化：

```ts
/**
 * 标记本事件是读取者在不认识 type 时可以安全跳过的。
 * 缺省意味着必需：读取者遇到未识别且无此标记的类型时，
 * 必须拒绝重建会话，而不是静默丢弃——
 * 因为一个不被理解的必需事件可能改变日志其余部分的解读方式。
 */
ignorable?: true
```

注释的后半句是点睛之笔：默认设为"必需"意味着忘记打标记的后果是**过度拒绝**（老程序拒绝读新日志，造成不便），而不是**静默吞掉**（老程序装作读懂了，实际丢掉了塑造重建的关键内容）。两种失误不对称——一个是显眼的麻烦，一个是隐身的炸弹。**把系统的默认值设在"出错时更吵闹"的那一侧**，这是贯穿 dsh 全库的失败哲学：让错误尽早、尽响亮地暴露，而不是被层层吞掉后在远处爆炸。
