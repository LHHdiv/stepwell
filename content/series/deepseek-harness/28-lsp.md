MCP 给了智能体"万物的工具"，但处理代码时它仍是个门外汉：找符号只能靠文本搜索，理解"这个函数被谁调用"只能靠猜。**LSP（Language Server Protocol，语言服务器协议）**补上这块短板——它是 VSCode 编辑器生态的底座：语言服务器进程持有语言的完整语法理解（类型推导、引用图、符号索引），编辑器通过 JSON-RPC 与之对话获得跳转定义、查引用、重命名等超能力。

dsh 的 `packages/lsp/` 把这套能力接进智能体。三包编队，老配方：

| 包 | 职责 | 角色 |
|---|---|---|
| `lsp/` | Service Definition：提供方注册表、逐查询选择、`ctx.lsp` | 接口 |
| `lsp-stdio/` | 通用多服务器 stdio 后端 | 实现 |
| （工具包） | 面向模型的 `lsp` 工具 | Consumer |

## 一、注册表的组织：id + 扩展名映射

ctx.lsp 的接缝词汇里有两个关键概念：

- **品牌化 id**：每个语言服务器提供方有唯一身份（又是第 05 讲的品牌家族成员）；
- **扩展名映射**：`.ts` 文件该问哪个服务器、`.py` 该问哪个——按文件扩展名路由查询。模型拿着"这个符号在哪定义"的问题进来，接缝自动找到正确的语言专家。

一个插件实例可以带一张**命名服务器表**，逐配置项注册隔离的提供方——TypeScript 服务器和 Pyright 可以在同一份配置里和平共处。

## 二、lsp-stdio：借来的世界

README 里最值得咀嚼的是这句设计宣言：

> 它通过 **ctx.fs** 读取，并通过 **ctx.subprocess** 启动，因此**服务器与源文件始终位于已挂载的执行世界中**。

回想第 22 讲的"执行世界"论断：把 fs 和 subprocess 指向远程沙箱，整个执行环境就搬家了。现在看到红利兑现实例：**LSP 不需要自己的远程方案**——因为语言服务器要开的进程走 subprocess（自动进了沙箱或远程）、要读的源码走 fs（自动是远程那边的文件），执行世界搬哪它跟哪。假如当初 lsp 自己直接调 Node 的 fs API，今天就得为每种执行后端单独适配一遍。**站在接缝上的包免费继承全部后端能力**——这是分层架构最动人的时刻。

## 三、"通用主机"的自我定位

README 还有一句清醒的免责声明：

> 这是**通用主机**，而不是语言服务器目录或安装器：部署需要显式配置命令与映射，预设应放在 cordis.yml overlay 中。

翻译：dsh 不会帮你下载 TypeScript 语言服务器、不会猜测你的 Python 解释器在哪。你必须在配置里写明每个服务器的启动命令和适用扩展名。为什么这么"不贴心"？因为语言服务器的安装方式千差万别且版本敏感——替用户做主只会制造更多玄学故障。**框架管接线，用户管选型**，职责清晰才可调试。这也和第 04 讲的装配哲学呼应：环境差异交给 patch/overlay 层解决。

## 四、逐查询打开：无状态的智慧

后端的一个技术细节见功力："查询时临时打开文档"。语言服务器协议要求客户端先"打开"文件才能查询它的语义——正经编辑器会维护一整套打开文档的状态同步。dsh 的做法是懒人式的：查询来了，临时把目标文件喂给服务器，查完即走。

代价是每次查询多一点点开销；换来的是**零状态管理**——不需要跟踪"哪些文件还开着"、不需要处理同步失配。对智能体的使用模式（高频次、单点查询）这是完全正确的取舍：一次跳转定义多花 50ms 无人在意，状态机的 bug 却会折磨所有人。**识别你的访问模式，再决定要不要为它建状态**。

> 💡 **知识拓展：为什么 AI 编程工具都在拥抱 LSP？**
> 纯文本视角的代码有大量歧义：同名方法、动态派发、跨文件重导出……grep 出十个结果，哪个才是真凶？语言服务器内部运行着真正的编译器前端，它的答案是编译器级别的准确。Cursor、GitHub Copilot 等产品都在把 LSP 信息注入模型上下文。dsh 的 lsp 工具让模型主动发起这类查询——从"被动接收文本"升级为"主动询问语义"，这是智能体编程能力的一次质变。
