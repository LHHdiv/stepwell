卷二到目前为止都在看"一个会话的内部"。但真实使用中你会积累几百个会话：上周让智能体改过的那个脚本在哪次对话里？某个 bug 是哪个祖先会话 fork 出来的？这些**跨会话**的问题需要一个专门的查询引擎——`session-query` 包向容器贡献的 `ctx.sessionQuery`。

## 一、它解决什么问题：两个世界的隔阂

先理清资源分布。会话数据活在两个地方：

- **实时存储 `ctx.sessions`**：内存里的活跃会话，快，但重启就没了；
- **持久化 `ctx.sessionPersistence`**：磁盘上的历史日志，量大管饱，但读取慢一拍，而且是**可插拔的**（下一讲细讲，后端可能是 JSON 文件也可能是 SQLite）。

没有查询引擎的话，每次搜索你都得自己写"先问内存、再问磁盘、结果去重、字段对齐"的胶水代码。session-query 把这套逻辑标准化成 `SessionQueryEngine` 约定：**它面对一份"组合语料库"（corpus）——实时记录与持久化记录合并后的统一视图**。

合并规则是本讲的第一个精华。同一个会话 id 同时存在于两边怎么办？源码约定：**只产生一条记录，实时事件优先**；同时用 `live` 和 `persisted` 两个标记报告各自来源的可用性。如果两边的不可变 header 冲突了呢？直接以错误码 `SESSION_QUERY_SOURCE_CONFLICT` 失败——还记得第 07 讲的失败哲学吗？header 是户口本，户口打架说明数据出了严重问题，绝不含糊调解。

## 二、读取面：七个方法速览

引擎的方法按用途分三组：

**列表与详情：**

- `listSessions()` — 列出全部会话元数据，实时优先合并，按确定的最新优先排序返回克隆；
- `readSession(id)` — 返回完整、脱离存储的原始日志。注意注释里的严谨：执行与恢复（resume）**相同的核心回放验证**，但绝不把该会话放进实时存储——查询就是查询，不许有副作用；
- `readSurface(id)` — 返回完整折叠后的当前表层（第 08 讲的 surface），并保证：压缩要么在替换追加之前被观察到、要么之后，**绝不会出现合成混合状态**。

**过滤：**

- `filterSessions(filters)` — 会话级谓词：id、工作目录、创建时间范围、父会话、来源可用性；
- `filterEvents(id, filters)` — 事件级谓词：seq/时间范围、事件类型、表层归属、语义文本。

过滤语法值得专门记：**过滤器数组之间是 AND，同一过滤器内的多个值之间是 OR**。比如"找最近一周里 cwd 是 /home 或 /tmp 的会话"= 一个时间范围过滤器 AND 一个值含两个元素的 cwd 过滤器。空列表匹配不到任何东西（而不是"不过滤"——避免手滑全量拉取），范围包含端点，格式错误的输入以 `SESSION_QUERY_INVALID_FILTER` 显式报错。处处都是第 07 讲那种 fail-loud 的味道。

**深挖：**

- `listEvents(id)` — 把每个事件分类为 `current` / `shadowed`（被 replace 顶掉的）/ `log-only`，用的正是共享的表层 fold——又是第 08 讲说的"单点投影规则"在别处的复用；
- `traceSession(id)` — 本讲的主角，见下节；
- `traceEvent(request)` — 追一个事件的来龙去脉：它的位置替换链、它引用的源事件链接。

## 三、traceSession：会话的家谱树

子代理（第 31 讲）会让会话产生父子关系：主会话 fork 出子会话，子会话再 fork 孙子……时间一长就是一片森林。`traceSession` 只读取一次语料库，然后返回两样东西：

1. **祖先链**：从直接父级向外追溯（带 `complete: false` 标记第一个缺失的环节）；
2. **后代树**：确定性的递归后代清单。

最有趣的是防御：**如果追踪路径成环（A fork B、B 又 fork 回 A），以 `SESSION_QUERY_INVALID_LINEAGE` 直接拒绝**。正常的系统不该出现环，一旦出现说明上游逻辑有 bug——查询层选择掀桌而非死循环。

另一个工程细节：所有接受取消信号的操作都承诺"信号会传递到每一个后端调用"，并且"每项操作都会等待已启动的后端调用结算，然后用信号的精确原因拒绝"。翻译成人话：你按了取消，它不会假装没听见，也不会留半拉子任务悬在空中，而是等在途操作落地后干干净净地告诉你"已按要求取消"。**取消也是一种必须正确处理的业务流程**，不是随手丢个异常。

> 💡 **知识拓展：为什么强调"与提供方无关"（provider-independent）？**
> session-query 的过滤逻辑全部跑在自己的抽象层上，不依赖 SQLite 的 WHERE 也不依赖文件系统的 glob。好处：换持久化后端（JSON ↔ SQLite ↔ 未来的云存储）时查询语义一字不变。代价：无法利用数据库的原生索引做深度优化。这是一个典型的**正确性优先于性能**的选择——对个人设备上的会话规模（几千个会话）完全够用。什么时候该把逻辑下沉到存储层？答案是等数据量真的成为瓶颈时，而且接口不用变。
