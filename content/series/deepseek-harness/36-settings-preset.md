卷七收官。前几讲的能力都各带各的配置，本讲看配置体系本身的两个主角：**settings**（用户可编辑配置的解析与存储）和 **preset**（智能体的按需组装单元）。

## 一、settings：三层解析

`ctx.settings` 服务约定的核心是值的解析顺序：

```text
最终值 = 用户文档分节          ← 最高优先（用户在设置文件里写的）
       ⊕ 注册方的组合 base     ← 插件自己的 cordis.yml entry 配置子集
       ⊕ schema 默认值         ← 兜底
```

逐层解释。每个插件注册自己 namespace 的 schema——声明"我接受哪些配置键、什么类型、默认值是什么"。这层 schema 不只是校验器，它还是**文档**：配置目录（docs/config-catalog.zh.md）就是从全仓库的 schema 自动生成的，第 04 讲 dump-config 看到的条目说明也源于此。

中间层的"组合 base"很微妙：插件挂载时 cordis.yml 里写的 entry 配置成为该 namespace 的基线，用户的设置文档可以在此基础上覆盖个别键。于是形成自然的权力梯度：**插件作者给默认，部署者定基线，终端用户做个性化**——三方各有话语权且互不越界。

还有一个容易被忽略但极其关键的兼容承诺："**不挂载提供方时消费方行为不变**：仍只按 entry 配置解析，因此任何组合有无 settings 都能工作。"翻译：settings 是纯增益组件——没装它，整个系统照样跑（只是不能改配置）。这是"可选能力不绑架核心"的标准姿势，对比那些"缺了配置中心就起不来"的系统，高下立判。

## 二、settings-file：写操作的三重敬畏

官方的文件提供方 settings-file 负责把设置落到 YAML/JSON 文档，README 对 update() 的描述值得逐句读：

> 在**写锁下先重读文档再原子写回**，保留**用户的 YAML 注释**、**当前未加载插件所拥有的分节**，以及**任何本进程尚未观察到的磁盘变更**。

一次写操作，三处克制：

1. **保留注释**：YAML 注释是用户写给未来的自己的便签（"# 这里改成 false 可以关闭遥测"），机器重写文件时把这些抹掉等于毁人手稿。为此实现必须做结构保持式的编辑而非序列化覆盖；
2. **保留未加载插件的分节**：你暂时禁用了某插件的设置段？文件里那段原封不动。卸载是临时的，用户的定制不该陪葬；
3. **合并进程外的磁盘变更**：别的程序（或另一个终端里的 dsh 实例）刚改过这个文件？先重读拿最新底稿，再做自己的修改——而不是用内存里的旧视图盲目覆盖。

三条合起来是一种态度：**写共享文件时假设世界在你不知道的地方运转着**。多进程、多工具共存的现实环境里，这种偏执是数据不丢的唯一保障。

## 三、preset：一份 YAML 就是一个智能体

卷八的装配主题提前预热。agent preset 的定义朴素到惊人：

> 一个目录，其中放置一份 `agent.cordis.yml`。把它挂载到某个 agent 的 **scope 上下文之下**，该会话就获得自己的工具与提示词段落。

回忆第 11 讲 scope 的两条规则：注册向下继承、事件向上扩展。preset 就是 scope 机制的直接消费者——挂载后，这块作用域里注册的工具清单和提示词段落只属于这个会话，"其他在运行的会话各自保持不变，因此**一个进程可以同时运行多个组装方式不同的 agent**"。

应用场景立刻涌现：同一个 dsh 进程里，你的"代码审查员" preset 只有只读工具+严格提示词，你的"文档写手" preset 有搜索和写作指引，主会话则是全家桶——三个智能体互不串台，共享同一个引擎。

闭环的最后一块在第 07 讲已经埋好：会话头部的 `agentPreset` 字段记录了本会话由哪个 preset 组装——注释说得很直白："预设决定会话的工具和提示词，恢复时若还原成不同组装，模型将面对无法执行的历史"。**持久化组装身份，是对未来会话的负责。**
