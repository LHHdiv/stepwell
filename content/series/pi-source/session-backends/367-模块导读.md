## 这个包是什么

给 `@earendil-works/pi-agent-core` 的 **harness Session** 提供一份 Node `node:sqlite` 实现。它实现的是 agent-core 的 `Storage` 接口 + `SessionRepo` 形态（`SqliteSessionRepo`），不是 coding-agent 主链那份 JSONL `SessionManager`。

分层：

```text
SqliteSessionRepo          目录、文件、create/open/fork/delete
  SqliteOpenSession        关闭时等已准入操作、关 db
    StorageBackedSession   【agent-core】树、分支、mutation
      SqliteStorage        实现 Storage：commit / scan / snapshot
        session/*.ts       表级 SQL
        001_initial.sql    schema
createNodeSqliteFactory    把 node:sqlite DatabaseSync 适配成 SqliteDatabase
```

权威耐久状态：`entries` + `scalar_values` + `list_values` + `usage_ledger`。`branch_*` 和 `sessions` 上的 message_count / usage_payload 是投影/缓存。

## 在执行链的哪一段

现行 `./pi-test.sh` 交互 / print **走不到**。那些路径用 coding-agent 的 JSONL 会话文件。

实验 `PI_EXPERIMENTAL=1 ./pi-test.sh server` 目前用 `JsonlSessionRepo`（`coding-agent/src/experimental/server.ts`），**也还没**换成本包。

谁在用：

- 本包 `test/*` 与 agent-core 的 storage/repo **conformance** 套件
- 将来的 harness 宿主（README 示例）
- 构建图：根 `npm run build` 会编这个包，因为它是独立发布单元，避免 `pi-agent-core` 默认拉进 `node:sqlite`

结论：主链、实验 server/client 现在都不调用。读它是为了理解「harness 的 Storage 合同」如何落在 SQLite 上，以及分支索引这类 JSONL 没有的结构。

## 依赖谁

- `@earendil-works/pi-agent-core`：`Storage`、`StorageBackedSession`、`prepareStorageCommit`、`createForkSnapshot`、`branchTip`
- `@earendil-works/pi-ai`：`uuidv7`、`Usage` 类型

运行时还依赖 Node ≥ 22.19 的内置 `node:sqlite`。没有 better-sqlite3。

## Storage 合同（读 SQL 前先看）

`packages/agent/src/harness/session/types.ts` 的 `Storage`：

- `commit(writes)`：一批 entry / usage / value / list 写入，返回 seq 与 stats
- `getEntries` / `scanEntries` / `scanBranch` / `scanBranchStructure`
- `getValue` / `scanValues` / `readList`
- `scanUsage` / `getStats`
- `close`

本包额外实现 `snapshot` 供同进程 fork 排队。`SqliteStorage` 用 **commit 队列** 把 commit 和 snapshot 串起来，内部 `db.transaction` 同步执行。

host 保证一个 Session 同一时刻一个可写所有者。Repo 拒绝进程内重叠的 create/open/fork/delete 同一 id，**没有**跨进程 lease。关 worker 再删。
