对讲机里很吵：阶段开始、思考片段、工具调用、旁白、正式讲解、引用、结束铃……若网页原样把每句都堆进大气泡，学生会以为「我去翻一下讲义」就是最终答案。前端的工作，是把直播间音轨剪成**看得见的课堂**：过程可以另开痕迹面板，板书才进助手气泡。

## 先连上统一对讲机

一句话定义：**流式事件（StreamEvent）**是后端推来的一帧课堂实况：类型、来源、阶段、正文、元数据、序号。为什么网页要自己懂协议？因为 HTTP 一问一答装不下「边讲边改气泡」。

客户端在 `web/lib/unified-ws.ts`：连 `/api/v1/ws`，带心跳与断线重连；重连后可用 `resume_from` / `subscribe_turn` 按 `after_seq` 续听，避免刷新就丢半堂课。事件类型与 Python 侧对齐：`content`、`thinking`、`tool_call`、`tool_result`、`sources`、`done` 等。

真正「发一句学生的话」时，浏览器发出 `start_turn`（或 `message`）载荷：内容、能力、工具开关、知识库、附件、语言、人格等——和上一讲书包字段同族。之后进入订阅：每一帧进来，交给聊天上下文归并。

> 小结：网页先当忠实听众，再当剪辑师。

## 剪辑规则：旁白进痕迹，板书进气泡

一句话定义：**旁白（narration）**是模型边调用工具边说的办事台词；**板书**是不按工具那一轮的讲解。后端聊天循环会给相关 `content` 打上元数据（如 `call_role`、`call_kind`）。前端在 `web/lib/stream.ts` 里做裁剪：

- `shouldAppendEventContent`：不是所有 `content` 都往答案上贴。
- `collectNarrationCallIds` / `recomputeAnswerContent`：一旦某轮被标记为旁白，就把那一轮曾贴过的字从「答案」里拿掉，避免复习笔记里全是「我找找看」。

`web/context/UnifiedChatContext.tsx` 维护会话消息与当前回合事件；流式过程中追加或重算助手正文，结束后再与落盘快照和解，防止后台快照把正在打字的气泡盖成旧稿。平滑打字感由 `useSmoothStreamText` 一类钩子处理：流式中按节奏吐字，结束后对齐全文，避免末尾「咔」一下跳变。

聊天气泡的呈现落在 `web/components/chat/home/ChatMessages.tsx` 一带：用户消息、助手回答、活动痕迹、问学生选项等分区渲染。你不必一次读完这个大文件，只要记住：**气泡吃的是剪辑后的答案，不是原始事件磁带。**

> 小结：同一句 `content`，元数据决定它进黑板还是进旁白轨。

## 断线、重讲、空白时先怀疑剪辑

学生说「屏幕转圈」：可能是 WS 没连上，也可能是回合还在跑但 UI 没订到事件。学生说「气泡空的」：可能是模型只在思考区说话（正文为空），也可能是全部被当成旁白滤掉，或 Markdown 判定为无可视内容。这些在最后一讲名词表与排错里会对到文件；本讲先建立预期——**空白不一定是后端没说话，也可能是前端按规定不展示。**

重新生成、编辑分叉、问学生暂停恢复，都会多发几种客户端消息类型；它们仍然落在同一条 WS 上，由运行时保证「同一回合」或「新开回合」。前端负责别把两条回合的事件拼进同一个气泡。

> 小结：排错时分清「没播音」和「剪掉了」。
