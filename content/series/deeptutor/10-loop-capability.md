数学课上，老师并没有换一间教室。他还是那套「讲一讲、算一算、再讲」的节奏；只是今天多了一张步骤清单：先写计划，做完一步勾掉一步，卡住了才允许有限次改计划。你若只看表面——「怎么又在检索、又在说话」——会以为解题和聊天是同一种课。你若只看产品菜单——「深度解题」单独一项——又会以为背后另有一台转圈机器。

真相落在两者之间：**选修课目录上多了一门课，炉灶却仍是聊天那口。** DeepTutor 的 **deep_solve（深度解题）** 把教法做成可挂上的钉子，而不是复制粘贴一整份 `while`。本讲顺着源码把「挂」字拆开。

## 入口很短：盖个戳，再走聊天流水线

打开 `deeptutor/capabilities/solve/capability.py`。`DeepSolveCapability` 继承的是和聊天一样的 **BaseCapability（能力基类）**——人话：一种完整玩法的合同（第 16 讲会展开）。它的 `run` 几乎只做三件事：

1. 在本轮书包（`UnifiedContext.metadata`）上盖 `solve_mode = True`，并算一个本轮专用的 `solve_session_id`（优先用 turn id，避免并发行抢练习本）；
2. 读设置里的最大轮数、重计划次数、温度、最大生成长度等，写进 metadata，并传给流水线构造参数——让设置页上的旋钮真的拧得动循环；
3. 创建标准的 `AgenticChatPipeline`，调用 `await pipeline.run(context, stream)`。

文件头写得很干脆，翻译过来就是：**不再有一份定制管线。聊天智能体循环本身就是求解器。** 简历里的 `stages` 现在也写成 `["responding"]`，不再假装另有 planning / reasoning / writing 三条独立流水线——那些职责改由「剧本 + 脊柱工具 + 同一套探索/结算礼貌」承担。

所以网页上点「解题」、命令行 `deeptutor run deep_solve "..."`，调度器请出的是名字 `deep_solve`；真正转圈的，仍是第 08、09 讲那台炉灶，刹车仍是「这一轮还点不点工具」。差别在点火前，有人往桌上多放了教具和一张课程说明。

> 小结：换玩法不等于换引擎；先盖戳，再进同一间教室。

## 循环插件：什么时候多几颗钉子

光盖戳不够。还要有人在「今天的工具名单」和「系统提示词」里认出：这是解题课。这份挂钩叫 **LoopCapability（循环能力 / 循环插件）**——人话：插在聊天循环上的教法附件，不是另起炉灶的整门选修课。协议写在 `deeptutor/capabilities/protocol.py`（注意：和 `core/capability_protocol.py` 里的完整玩法基类不是同一个文件）。

解题对应实现是 `deeptutor/capabilities/solve/loop.py` 的 `SolveLoopCapability`：

- `name = "solve"`，`owned_tools` 声明三颗自有工具名；
- `is_active(context)`：看 metadata 有没有 `solve_mode`——没盖戳就当普通聊天，不插手；
- `system_block(...)`：激活时返回一块 `PromptBlock`，内容来自中英文 `prompts/.../system.md`（也可被配置覆盖）——这就是「今天怎么解」的剧本；
- `augment_kwargs(...)`：模型点脊柱工具时，服务器注入 `_solve_session_id`，并按设置刷新该会话的重计划上限。模型不填这把钥匙，也改不了。

协议注释里有一句产品公理，值得用中文记牢：解题 / 掌握度这类插件**复用聊天完整工具面**，用户在作曲器里打开的网页搜索等开关，解题课同样尊重；插件只**追加**自己的工具，不擅自拆掉用户已选的按钮。例外是「知识型」插件会独占工具面——那是另一门故事，第 15、16 讲会碰到。

聊天流水线在组 `enabled_tools` 时，会把当前激活插件的 `owned_tools` 叠进名单。于是同一口炉灶上，模型忽然多看见 `solve_plan` 几颗键，并且系统提示里多了一段「先计划再动手」的教法。

> 小结：循环插件 = 条件激活 + 追加工具 + 追加剧本 + 私有参数；不替换整台循环。

## 三颗脊柱工具：计划、勾一步、有限次改图

钉子的实物在 `deeptutor/capabilities/solve/tools.py`。对外兼容入口 `deeptutor/tools/solve_tool.py` 只是把符号再导出一遍，方便登记表引用。三颗名字与课堂含义：

| 工具 | 课堂含义 |
|---|---|
| `solve_plan` | 先交步骤清单（通常建议 2～6 步；简单题一步也行） |
| `solve_finish_step` | 宣布某一步做完；可触发上下文检查点，把刚完成的工具絮语折成一行摘要 |
| `solve_replan` | 卡住时改计划，次数有上限 |

`tools.py` 文件头把设计公理写清楚了，翻译过来是：**智能住在循环的出口——模型自己想怎么解每一步；确定性的脊柱（承诺计划、不许跳步、有界重计划）是引擎状态，通过工具读写。**

换句话说：`while` 不会变成「状态机硬编码每一步公式」；它只保证教学结构。计划、进度、剩余重计划次数，存在内存里的 `SolveSession`（`session.py`），用本轮 `solve_session_id` 隔离。步骤 id 由服务器生成（`S1`、`S2`…），模型只写目标描述，不能随便发明存储键——这是小而硬的安全与一致性细节。

课堂上学生感受到的差别，往往不是「又换了一个模型」，而是老师会不会说：「先把步骤写在黑板上。」`solve_plan` 强迫先交清单；`solve_finish_step` 强迫一步一勾——勾完还可以触发上下文检查点，把刚那一步里啰嗦的工具来回折成一行摘要，免得对话窗口被草稿淹没。`solve_replan` 则承认计划会错，但改图次数有顶，避免「我再换一种思路」变成无限循环。

对照第 02 讲提过的分家，现在可以更硬一点：

- **聊天**：求讲清楚；刹车 = 不再点工具（可加第 09 讲的礼貌）。
- **解题**：求按步骤；炉灶同上，多脊柱工具与剧本；设置页的最大轮数、重计划次数会经 metadata 拧到同一套循环上。
- **出题 / 研究**：更常自管流水线，并用 LABEL 灯当交卷信号（下一讲起）。

「挂在聊天上」省下的不是聪明，是重复：检索、提问学生、截断续写、结算、强制收尾，聊天已经会；解题缺的是「清单纪律」。把纪律做成工具而不是硬编码公式，也留下空间：换一个学科的剧本（`system.md`），同一套三颗钉子仍能用。

若有人问「那掌握度呢？」——同一设计家族：也是盖戳 + 循环插件 + 自有工具，结束条件更硬（题型过关）。本讲不展开，只要知道：**挂聊天**是 DeepTutor 教法插件的惯用姿势，不是解题特例。

> 小结：换的是课表和钉子，不是教室的墙；纪律在工具里，聪明在模型里。
